# Project (experimental)

Project discovery, a persistent design conversation, an auditable record of **human** decisions, isolated prototype variants, and iteration state with human-confirmed stage gates for design → prototype → implementation → acceptance. Prototype work is available through explicitly opened variant conversations. English spec review and explicitly started single-agent batches are available. Automated acceptance, shipping, budgets, workflow/swarm execution, dashboard integration and archive workflows are **not available yet**. Advancing a stage never starts implementation automatically.

Requires Amira extension API **0.1.53** (owned conversations arrived in 0.1.51; native conversation focus in 0.1.52; scoped file tools, inherited execution descendants and permission-checked owned tool calls in 0.1.53). No workflow, swarm, btw or dashboard dependency.

## Commands

Run commands from the **main** conversation:

| Command | Action |
| --- | --- |
| `/project` or `/project list` | Choose from previously opened projects plus the nearest discovered project. No disk scanning. |
| `/project new [name] [--root <directory>] [--language <tag>] [--commit-documents]` | Create and attach a project. Without a name, ask for one. Default directory: current working directory. Quote names/directories containing spaces. |
| `/project switch [name, id, or directory]` | Attach a known/discovered project, or open an explicit directory. Without an argument, show the picker. Duplicate names require an ID or directory. |
| `/project status` | Show attached directory, iteration, real stage/status, pending approval, manual-trial status, and accepted/skipped/unresolved batches of the pinned plan. |
| `/project next` | Show the current saved summary and proposed next step; ask you to confirm, choose an alternative or skip. A batch pass proposes fresh approval of the next batch, not overall completion. No implementation starts automatically; from implementation planning, offers spec generation and review. Escape dismisses the next-step menu without changing its saved proposal or generating a spec. |
| `/project skip <stage>` | Ask you to explicitly skip the current stage (`design`, `prototype`, `implement`, `accept`). Skipping acceptance lists and records every remaining pinned-plan batch as skipped, not passed. |
| `/project skip batch` | From a non-running pinned implementation or acceptance boundary, explicitly skip the current batch. Interrupt running work first. Its receipt identifies the exact plan/batch; remaining work still needs human approval. |
| `/project revisit design\|prototype` | Return to an earlier stage without resetting changes. During implementation/review, choose interruption or waiting until the batch finishes. |
| `/project design` | Open this project's saved design conversation for the current iteration. |
| `/project prototype` | Propose, edit or remove variants, then confirm a list of 1–3 variants before opening prototype work. |
| `/project prototype <variant>` | Focus the saved conversation for a confirmed variant in this iteration. Opening it does not start a model turn. |
| `/project prototype choose` | Choose a recorded variant or None, then enter a separate human reason or explicitly skip the reason. |
| `/project prototype run <variant>` | Display only the recorded run command and working directory. Never execute it or start a server. |
| `/project spec` | Generate an English spec from verified decisions and confirmed prototype conclusions, with a user-language summary. Review the rendered items/checks/plan, approve that exact revision/hash and plan, request regeneration with feedback, or cancel. From design, approval explicitly skips prototype. |
| `/project implement` | Start the approved single-agent batch after committed-base/Git setup review, or focus its live coordinator. F6 returns to main without stopping it. |
| `/project help` | Show command help and the batch boundary. |

Example: `/project new "Local planner" --root "./work/planner" --language en`.

**Attaching is metadata-only:** the main conversation's working directory does not change. The design conversation and research children use the selected project directory. One project is attached per main session. Attachments follow that session's branch (including resume/fork/rewind); the latest snapshot wins. An attachment receipt is persisted even before the first model prompt. Memory-only hosts cannot promise next-run attachment persistence.

The panel above the input shows name, iteration, the persisted stage/status and the next-step suggestion. It does not infer approval from tool completion or start work while rendering. Before opening design it says “Open design conversation.” Once a design runtime is available it uses a neutral continuation/F6 return hint, not a command to open the conversation again. Host panels receive the main session ID even during native design focus, so the extension does not claim to infer focus from that ID. The host's native focus indicator identifies the actual composer target. The normal panel-collapse control leaves the summary line visible. Missing/invalid status appears before long paths in picker labels; the extension never silently substitutes a nearby project.

## Discovery and files

The nearest ancestor containing `.amira/project.json` wins, including nested projects inside one repository. A malformed nearest marker is an error, not permission to fall back to an outer project. An explicit switch resolves its directory/registry identity independently of cwd discovery, so you can recover by switching to a healthy project. Lists retain healthy registry entries alongside a visible discovery warning. A directory has exactly one project marker. The registry in the host-assigned extension `dataDir` only remembers projects opened before; it never scans search roots or your disk. Registry writes publish independent immutable transactions in `registry.entries/`, so different Amira processes cannot lose each other's read–modify–write updates. Legacy registry snapshots are still read. Healthy explicitly reopened locations outrank stale same-ID locations even if the wall clock moved backwards; stale identities remain visible when no healthy location exists.

```text
<project>/
  .amira/
    project.json              # schema version, stable ID, name, created time,
                              # currentIteration, settings.language/commitDocuments
    project/
      design.md               # model-maintained design document
      decisions.md            # generated human-confirmed ledger, including history
      suggestions.md          # unconfirmed model proposals, never decisions
      research/               # generated filenames for research notes
      prototypes/<iteration>/<variant>/ # disposable code; ignored by default, never promoted
      iterations/1/
        state.json            # recoverable stage state, revision, approvals, skips, artifact links
        .state/               # authoritative immutable, hash-chained revision records
        artifacts/            # <closed-kind>-<generated-UUID>.json with identity + payload
        .writer.lock          # transient iteration writer claim; dead-process claims recover
                              # retained .preserved versions may remain after publication
      decisions.evidence.jsonl # authoritative human-answer records (created on first answer)
      decisions.manifest.json  # acknowledged generated Markdown hash
      decisions.generated.md  # conflict-only projection; never overwrites hand edits
```

Creation preserves existing `.gitignore` content and appends `.amira/project/` unless `--commit-documents` is selected. The marker is not ignored. Changing `settings.commitDocuments` later does not remove an existing ignore rule; review `.gitignore` yourself if you decide to commit the documents.

The extension's document writers use only fixed documents, evidence and generated research-note filenames. Prototype code is written separately through host file tools scoped to a confirmed variant directory. Canonical root, ancestor and output-directory identities are pinned when a project is captured, then checked again before writes and publication. Replacing a root or captured ancestor with a junction is rejected even if the redirected tree contains the same project marker. Traversal and symlink/junction escapes are rejected. External output directories are not supported in this batch. These are application safeguards, **not an OS sandbox**: portable Node APIs cannot eliminate the last kernel-call race against a hostile process continuously swapping directories. Allowed read tools may read outside the project according to host permissions.

## Iteration stages and approval gates

State lives in `.amira/project/iterations/<n>/state.json`, not the host session database. It records `schemaVersion`, monotonic `revision`, project/iteration identity, stage (`design`, `prototype`, `implement`, `accept`), status (`idle`, `working`, `awaiting-confirmation`, `interrupted`, `blocked`), skips, human approval receipts and immutable artifact links. Opening an old batch-one project creates **design / idle** state lazily; it never rewrites old documents or decision evidence. Reopening state is inert: it never replays a launch.

The reducer keeps these events separate: **work finished → summary prepared → transition proposed → human confirmed → next stage started**. A model recommendation or a tool finishing is not approval. Proposals are saved before a human dialog, and receipts bind the exact project, iteration and state revision. Implementation/review authorization also pins the **spec revision/hash and immutable batch-plan artifact ID/hash**, batch ID and mode (plus the implementation model). Batch membership is resolved only from that pinned plan, never from the newest plan or any plan with the same batch label. Publishing a replacement plan invalidates an idle confirmed launch authorization; a new summary and same-stage `reapprove` proposal require fresh human confirmation. Plan replacement is refused while work or approval is in progress. Dismissing a dialog creates no approval receipt. If anything changes while a dialog is open, the stale answer fails; review the new state and confirm again. The state store serializes writers, uses a cross-process claim, and rejects stale revisions rather than silently overwriting another writer.

Each artifact has a closed kind and an extension-generated filename under the iteration directory; titles, model output and supplied text never choose output paths. The kinds cover stage summaries, spec revisions with stable item IDs, batch plans, acceptance verdicts keyed by spec item ID with actual check records, manual trials (`pending`, `tried`, `problem`, `deferred`), and corrections/impact. Artifacts are immutable; edits are detected instead of overwritten. State publication flushes files and uses an atomic, no-clobber hard link for each immutable journal record; `state.json` is a safely replaced projection, with directory flushes where supported. A journal record is the commit boundary: recovery validates all referenced artifact envelopes and batch metadata **before** repairing an older/missing projection or writing its acknowledgement, and never replays work. Unsupported or invalid referenced evidence leaves the old projection bytes/inode and acknowledgement state untouched. A live cross-process claim fails clearly; a dead process's claim is recovered with a token-specific recovery claim. Manual edits to state or artifacts block further writes and remain byte-identical. Preserve retained versions when recovering a crash or manual edit.

Batch membership is recorded in store-owned `batchManifests`, copied from hash-checked plan artifacts, and progress in plan-bound `batchResolutions`. A consumed batch pass and its resolved manual trial become accepted progress only through a human-confirmed transition. `/project next` presents the batch summary and proposes the **next unresolved batch** for fresh implementation approval, with the exact spec/plan/batch/mode/model context. Confirming it leaves implementation idle; it does not start an executor, and it never carries the previous batch's changes pointer into the new work. A cancelled or stale dialog records no batch resolution or launch authorization.

**Overall acceptance is not a single-batch verdict.** Completion is proposed only after every batch of the pinned plan has a confirmed passing resolution or an explicit human skip. If any batch was skipped, overall completion is labelled **skipped — not a pass**, never “Accepted.” Failing, blocked, interrupted, merely published, or manual-trial-pending verdicts do not resolve a batch; earlier plan/spec revisions cannot satisfy a new plan. Legacy draft completion is interpreted only from verified consumed evidence and human receipts, never by inventing outcomes for remaining batches; historical bytes are not rewritten.

Corrections use **qualified `acceptedBatches` references**, not bare batch labels. Each reference identifies the owning spec artifact/revision/hash, plan artifact/hash, batch ID, accepted-resolution human receipt, and consumed review attempt. Both publication and correction consumption require an actual confirmed, accepted `batchResolution` with matching passing evidence and any required resolved trial. Published-only, interrupted, unconfirmed, pending-trial, skipped, and same-label/different-plan results do not qualify. A correction targeting a revised spec may reference a genuinely accepted batch of an older plan; that older owner's identity remains explicit. Legacy unqualified claims are not silently promoted into accepted evidence.

Each acceptance start captures a fresh **stage-attempt ID, review ordinal and code-snapshot hash**. Verdicts and manual-trial artifacts bind all three, along with the exact spec and batch plan, at both publication and consumption. A verdict saved for an interrupted attempt remains readable history; a continuation needs a new attempt and new verdict, even when the code snapshot is unchanged. Merely copying a batch label or increasing a numeric attempt field cannot authorize stale evidence.

Skips retain your choice and never fabricate output: a skipped prototype has no chosen variant, and skipped acceptance is **not passed**. Acceptance failure retains failing spec item IDs and proposes a human-approved return to implementation; it never starts a hidden retry loop. An automated UI pass is **batch accepted, manual trial pending** until you record that you tried it or explicitly deferred it; deferred never means tried, and the batch cannot advance or complete while the trial is unresolved. A human-confirmed **problem** on the active attempt proposes a separate, human-confirmed repair back to implementation for that same pinned spec/plan/batch. The automated verdict remains unchanged, and the manual finding/receipt remain history. The repair needs fresh implementation, acceptance, and trial evidence before that batch can be accepted; simply changing the old problem to tried/deferred is not a repair. Pending transitions and unresolved revisits take precedence over trial dialogs. Interrupting or leaving a review retires its live trial pointer while preserving attempt-bound trial artifacts as history; explicit continuation never resurrects an interrupted attempt's trial. Trial recording is offered only for the matching eligible active review.

Revisiting design/prototype during implementation or acceptance interrupts the running attempt and retains its changes pointer, or queues the revisit until a safe batch boundary if you choose to wait. Pending revisit requests are separate from returned/cancelled revisit history and correction obligations. “Continue current stage” explicitly cancels the outstanding request as well as its proposal; it does not silently resume interrupted work or erase duties from already-returned visits. An unentered cancelled request requires no invented correction; explicit continuation can resume against the unchanged approved decisions. A restart between summary publication and proposal publication reuses the saved summary to reconstruct the pending revisit. Returning and advancing again permits another revisit without losing earlier receipts or unresolved obligations. Accepted **and skipped** acceptance leave the iteration open: a confirmed revisit clears the current completion designation while preserving historical verdicts/skips. Existing changes and earlier artifacts remain; there is no Git reset, transcript rewind or prototype promotion. Correction artifacts link superseded → new decision IDs, affected spec item IDs and changed files, so later execution can approve a correction batch rather than restart from scratch. Every outstanding executable-work correction must be mapped against a revised spec before execution can resume. Single-agent implementation now uses these gates; acceptance execution and automatic impact generation arrive in later steps. Their state and evidence model remains available without a reviewer.

`/project next` does not invent a completed summary. If no stage output is ready it explains the missing gate. You can continue design or explicitly skip it. Saved design can be finalized into a summary with its confirmed decision IDs, then proposed for the next stage. “Continue current stage” cancels a pending proposal and invalidates the prepared design summary. A stranded design attempt after a crash requires explicit interruption/continuation confirmation; the interrupted record is retained. Design writers share the iteration claim, invalidate captured state revisions before publication, and reject late questions after a revision or stage change. During a stage change the local design runtime is stopped/drained before confirmation is committed. Completing or skipping prototype can enter implementation **preparation only**, without authorizing execution. Starting implementation still requires the exact saved spec/batch/mode/model approval; acceptance still needs the approved existing-change context. `/project spec` produces those pinned artifacts and approvals. `/project implement` is a separate explicit launch. At the acceptance boundary the command reports **acceptance: coming next**, without running a reviewer. Prototype conversations are opened explicitly with `/project prototype` commands, not by advancing a stage.

Storage failures expose structured diagnostic reasons. Commands and panel errors use the effective batch-one language policy (`en`/`zh`/`ja`), including stale revision numbers and recovery actions. A freshly validated marker supplies the language even if iteration loading fails immediately, including after resume without a panel refresh. Unsupported numeric schema versions in markers, journals, state and artifact envelopes report encountered/supported versions and compatibility instructions, separately from malformed data or a broken hash chain; no such error is repaired by deleting or rewriting evidence. Artifact compatibility tests use coherent hashes and projection receipts, and verify byte preservation.

## Design conversation

There is **one owned conversation per project ID and iteration**. Reopening is inert: it does not call a model or replay an unfinished question. Enter a message to continue. A new iteration uses `design.md` and `decisions.md`, never the previous iteration's transcript. Iteration advancement is not implemented; new projects start at iteration 1.

The native transcript and composer are shared visually, not operationally. Main work keeps running. **F6** returns to main; **Esc** also returns when the design conversation is idle and its composer is empty. While design is working, Esc/Ctrl+C stops design only. Drafts, history and question dialogs are handled by the host. Slash commands must be run after returning to main. The host focus indicator shows main status/pending attention.

Design history survives main `/clear` and `/resume`. Closing focus does not stop/release it. A second process holding the design conversation gets an **in use** error. Host unload/exit stops and releases runtime resources without deleting saved history. Unsupported hosts explain the missing capability; there is no ephemeral-session fallback.

### Tools and questions

Research operations are restricted to `read`, `grep`, `glob`, `web_search`, `web_fetch`. `ask_user` and the fixed extension tools `record_decision`, `record_suggestion`, `save_research_note`, `update_design_doc` and `project_research` provide the control plane and constrained output writes. No arbitrary `write`, `edit`, shell, `agent`, worktree, workflow or swarm tools are admitted. Web availability still depends on the host; the extension does not make its own network requests.

The model is instructed to lead with multiple-choice questions: recommended option first, each description explaining trade-offs. Previews are text, code, tables or ASCII only. Questions appear as normal human dialogs in the focused transcript. The extension never asks the main model to answer on your behalf.

`project_research` starts fresh-context, read-only children through the owned conversation's `createGroup`. Their tool ceiling cannot widen, their cwd is fixed, and they cannot ask or confirm decisions. Only the extension's constrained note writer saves research output.

### Evidence and recovery

Only validated human dialog answers become decisions. A model-authored recommendation remains in `suggestions.md`. Each decision retains an ID, actual confirmation date, full question/options/trade-offs, exact selected labels or free-text alternative answer, language, and an ask-record reference. “Other” is an alternative choice, **not** a rationale. No reason is inferred from it or from a model recommendation; a rationale requires a separately requested human explanation. Cancelled, unavailable, aborted or invalid responses do not create decisions.

Before returning an answer to the model, the extension durably writes structured evidence under `.amira/project/` (JSON lines, with file flush). Cancellation is checked after entering the per-project queue and immediately before publication. The final identity check, rename, directory flush where supported, and cleanup form a short non-yielding commit section. The owner receipt **does not wait on Markdown I/O after that commit**: a later ordinary event-loop Stop cannot overtake its acknowledgment. Cancellation processed before publication produces no decision; successful publication is the extension's commit boundary. `SessionData.append` is not used as a durability acknowledgment.

Markdown is a derived projection, scheduled separately after owner-answer acknowledgment and retried on the next design open. Projection failures/conflicts are reported separately, never turned into a false declined/no-decision receipt. A process crash between evidence publication and host acknowledgment cannot be a filesystem/host transaction; the durable human evidence remains authoritative and recovery does not infer a new answer from prose. Superseding requires a new human confirmation and preserves the old record (`supersedes D3`, with the reverse link in the ledger).

Generation metadata tracks `decisions.md`'s hash. If you edit it by hand—even during generation—the extension preserves the actual edited inode and generates a sibling `decisions.generated.md`. Publication uses retained versions plus no-clobber hardlinks, not a stale hash check followed by unconditional replacement. Design/suggestion tools likewise report conflicts and their actual sibling output paths instead of claiming the named file was updated. Hardlink support is required; unsupported filesystems fail before moving the original.

Hidden `.preserved` versions intentionally remain: an editor holding an old writable descriptor may still save into one. Do not remove them while editors may hold those files. There is a brief pathname gap between retaining an old file and publishing its replacement; after a crash, a retained version may need restoring, especially for human-only annotations. The evidence can always regenerate confirmed decisions, but cannot reconstruct handwritten annotations that were never evidence. Do not manually edit evidence or generation metadata.

Legacy evidence from the rejected writer remains byte-for-byte intact and its original hash chain is verified separately. Corrected semantic views, Markdown and new-iteration model seeds no longer treat its automatic `Other` copy as a rationale; they mark that legacy explanation as unverified. New projection records explicitly distinguish this corrected interpretation from historical bytes.

## Prototype stage

At the prototype stage, `/project prototype` presents a **proposal**, not an approved plan. Review the proposed variants, edit their descriptions or remove variants, and explicitly confirm the final **1–3 variant** list. Model suggestions, a dismissed dialog and an edited draft are not confirmation. Variant work belongs to the current project and iteration; reopening saved work does not replay a launch or begin a model turn.

Each confirmed variant has its own conversation. Send the build request in its focused native composer; opening or reopening is inert. The model finishes with one run command and a structured report; the extension validates its cwd and saves the manifest, rather than letting the model edit stage artifacts. `/project status` and prototype commands refresh completed reports. On an older host, the prototype command asks you to upgrade to API 0.1.53 or newer and never starts an unconfined session. `/project prototype <variant>` focuses it through the host's native conversation UI; return to main before issuing project commands. Host **file-tool writes have exactly one allowed root per variant**, `.amira/project/prototypes/<iteration>/<variant>/`, not the production project root or a sibling variant. The host enforces that write scope for file tools; reads still follow host permissions. Shell tools still use the **current permission mode**: a variant cwd is **not a shell sandbox**, and shell commands may affect files outside that directory if host permissions allow them. Review permissions and commands accordingly.

New variant conversations use `<projectId>/iteration/<n>/prototype/<variant>` and the host's `apply_patch` tool. Older saved conversations with the mistaken `patch` ceiling are not widened or rewritten. Read-only inspection remains on the old conversation; explicitly reopening it for editing creates a bounded `/policy/apply_patch-v1` conversation and preserves the previous ID/transcript in the extension-owned mapping. A notice identifies both sessions, and no messages or commands are replayed.

Prototype directories are ignored by default with `.amira/project/`, subject to the existing `--commit-documents` setting and your `.gitignore`. They are disposable exploration, not production implementation. Choosing a variant **never promotes or copies its code into production**, changes production imports, or starts implementation. Comparison is **read-only**: inspect recorded summaries, trade-offs and results without modifying variants or executing their programs.

Use `/project prototype choose` to explicitly select a variant or **None**. The human reason is requested separately from the choice: enter your explanation or explicitly choose **Skip reason**. An empty or cancelled reason is not an implicit skip, and neither an option label nor a model recommendation is treated as your explanation. Choosing None retains the findings without selecting code. To skip the stage itself, use `/project skip prototype` and explicitly confirm the skip. A skipped stage has no chosen variant and does not invent a successful prototype. If you decline a prototype skip, `/project next` → **Continue current stage** abandons that skip summary and restores a confirmed/idle editing boundary. Reopen a variant explicitly to continue; earlier attempts, files and decision evidence remain history, and no work or command is replayed.

`/project prototype run <variant>` **only displays the recorded command and cwd** so you can inspect and run them yourself. It never executes a command, installs packages, opens a browser, starts a server or automatically restarts anything. Missing run information is not permission to infer a command. A `ready` status means the model supplied a structurally valid report with an in-variant cwd; it is not an independent claim that the command was executed or passed checks. Comparison's file count is the current prototype output tree, excluding `.git`, `node_modules` and symlinks, not a production Git diff.

Prototype decisions use evidence **format version 3**: the selected variant (or None), immutable manifest pointers and separately captured `reason` or `reasonSkipped` are recorded together. Existing v1/v2 evidence and hash-chain semantics remain byte-identical. A restart finishes missing choice/summary bookkeeping from this evidence without asking again or duplicating decisions, and never replays prototype work. A confirmed revisit reopens the variant list while retaining prior conclusions, files and native transcripts. A revised selection—including None—automatically supersedes the prior active prototype conclusion for that iteration. Recovery preserves those supersession links without duplicating decisions. Historical evidence remains readable even if disposable prototype output is removed; opening or displaying a runnable command validates the current paths again.

### Advisory: references to the prototype directory

`scanProductionPrototypeReferences(root)` in `src/prototype-boundary.ts` is a **read-only conservative text scan**, not an import parser, dependency audit or isolation guarantee. It returns `{ file, line, column, text }`: project-relative forward-slash filenames, one-based source lines and UTF-16 columns, and the original matched namespace text (including escapes). `formatPrototypeReferenceReport()` prints `file:line:column` and that matched text under the header **“Advisory: references to the prototype directory.”** The old `scanProductionPrototypeImports` export remains a compatibility alias, but its results are now references, not import violations.

Each physical source line is searched for `.amira/project/prototypes` after decoding JavaScript `\\xNN`, `\\uNNNN` and `\\u{...}` escapes and CSS hexadecimal escapes (with optional terminating whitespace), normalizing backslashes/repeated slashes, and folding ASCII case. This catches template expressions, parentheses, erased TS wrappers and all entries in Sass lists without interpreting their syntax. **Comments, ordinary strings, regexes and JSX text may also be flagged**, including references that are not actual imports; inspect their context. Path fragments split across lines or assembled by concatenation are **not reconstructed**, and dot-segment paths, aliases and computed module resolution are not evaluated. No project code/configuration or run command is executed, and no TypeScript/compiler/parser runtime dependency is required. TypeScript remains a development dependency for typechecking only.

The file set is JS/TS (`js`, `jsx`, `ts`, `tsx` and their `c`/`m` forms), CSS/SCSS/Sass/Less, and common configuration files (`json`, `jsonc`, `yaml`, `yml`, `toml`, `ini`, `cfg`, `conf`, `config`, `.env`/`.env.*`, dot-rc files, `.gitignore` and `.gitattributes`). The project's `.amira/project` tree, `.git` and `node_modules` are hard exclusions. Conventional build/cache names (`dist`, `build`, `out`, `target`, `coverage`, `.next`, `.nuxt`, `.output`, `.svelte-kit`, `.cache`, `.turbo`, `.vite` and `.parcel-cache`) are heuristics **only for untracked paths**. A read-only `git ls-files` snapshot keeps tracked source/style/config files and the ancestor directories needed to reach them eligible—even under names such as `src/build` or `src/target`. Untracked output siblings remain excluded, and tracked status never overrides the hard exclusions or symlink safeguards. Native Git supplies the effective ignore rules, including parent/nested `.gitignore`, `.git/info/exclude`, configured `core.excludesFile`, default user excludes, negations and tracked-file semantics. Inherited Git directory/index/config-injection/trace overrides are stripped; hooks and executable filesystem monitors are disabled. Non-Git projects use temporary Git metadata outside the project to honor local `.gitignore` files. Git is required for filtering; there are no hooks, index writes, network requests or source-tree initialization.

Implementation and acceptance **show advisories, never automatically block on their matches**. The implementation result includes an added-diff-line advisory gathered through the coordinator shell (not the scanner's direct Git probes); it does not prove the absence of copied code or dependencies. The complete source-tree scanner remains available for manual advisory presentation. Use `reportProductionPrototypeReferences(root)` for presentation: scan failures are shown as **“Scan unavailable”**, not as a clean result or an automatic failure of the stage. The low-level scanner still throws on filesystem/Git failures. Descendant symlinks/junctions and source-file links are not followed; a linked root is rejected and canonical paths/file identities are checked before reading. This is not an OS sandbox against hostile concurrent directory replacement. Run the offline regressions with `bun test test/prototype-boundary.test.ts test/prototype-scan-ignore.test.ts`.

## Language

Precedence: **project `settings.language` > extension Document language > user's conversation language**. Select the effective source before validating it; an invalid lower-priority setting cannot block a valid project override. An explicit project value of `conversation` follows the human conversation, not the extension default. Edit the marker's project setting when you want a project-specific override. Language changes affect **new content only**, never retranslate past evidence or documents automatically.

Already-open design runtimes follow these changes without reopening: extension-setting callbacks update their current policy, and every model continuation re-reads the captured project's marker settings. New document tools and new questions refresh and capture their effective language too; no filesystem watcher or automatic model turn is started. A question already shown to you retains its presented language through the answer, evidence and receipt. Subsequent work uses the new effective setting. The saved conversation spec/history and existing documents are not rewritten.

Generated text supports **English (`en`), Chinese (`zh`, including `zh-CN`) and Japanese (`ja`)**, including regional tags in these language families. Any other valid tag falls back to English, with an explicit notice once per unsupported tag per extension run. The requested tag remains in project settings; new evidence records the effective output language. Invalid tags are not silently accepted.

Chinese/English/Japanese human turns can be inferred conservatively (Japanese kana is checked before Chinese Han characters); if there is no reliable signal, creation/design asks for a language tag. Terminal locale and model/agent messages are not authoritative. Model-facing instructions remain English with a one-paragraph summary in the effective user language. Ledger scaffolding, suggestion headings, status/panel summaries and the design introduction use the same localization policy.

## Spec and single-agent implementation

`/project next` offers spec generation from the design next-step menu or after prototype/implementation planning. You can also run `/project spec` directly after design, after a confirmed prototype choice, or after explicitly skipping prototype. Generation uses text-only `complete` with **no tools and no inherited conversation history**. Only verified, non-superseded decisions, the human-confirmed prototype choice/pointers and prior spec revisions enter it; neither design Markdown nor the design transcript is supplied. A feedback regeneration retains immutable old specs/plans. Stable item identity is enforced by extension-controlled, predecessor-bound lineage, not prompt compliance alone: edits retain an existing ID, additions receive fresh extension IDs, and removals must be explicit. Silent renumbering is rejected before publication. Malformed output, unknown decision IDs, missing check cwd, orphan exact checks, or incomplete batch coverage fails closed.

The rendered review starts with a summary in the effective document language, then the English goal/constraints, numbered stable-ID items, per-item acceptance criteria, exact check commands and their cwd, and an ordered single-agent batch plan. It shows the spec/plan hashes, requested implementation model and any skipped prototype stage before approval. A pending approval reopened with `/project next` renders the pinned spec/plan again. Approval is an existing stage-engine human receipt, not a model assertion. No Git or implementation starts from the review. Use `/project implement` separately.

Git discovery, setup, snapshots and checks use **owned `runTool` shell calls under your current permissions/rules**, never `api.runCommand` after an unrelated confirmation. Plan mode or a denied command stops setup. Every initial setup shows the exact committed HEAD, repository, destination branch/worktree and dirty/untracked preview. You may stop and resolve local changes or explicitly exclude **all displayed local changes** from that commit. No stash, copy, hidden dirty snapshot or silent omission is used. Both status probes use `--ignore-submodules=none`: configured submodule ignore modes cannot hide staged/unstaged/untracked contents or a changed submodule HEAD. The preview is checked again before setup.

For an empty/no-commit project, confirm `git init` if needed plus an **empty initial commit** before setup. Existing files are never staged. A staged index blocks the empty commit. Git uses your existing identity, signing and hooks; failure stops with the command/error, with **no** `--no-verify`, signing override, alternate hooks or identity injection. Resolve it yourself and retry. Stack/dependency/test scaffolding belongs in the approved first batch's worktree, not the original directory.

The extension journals a planned worktree artifact before creation and a ready artifact after verification. The branch is `amira/project/<projectSlug>/iteration-<n>`; the slug includes a normalized name plus a filesystem/ref-safe component derived from the stable project ID, distinguishing same-named/subdirectory projects. Normal lowercase generated IDs retain their spelling; unsafe, case-ambiguous, or reserved IDs use an `id-<SHA-256>` component. Marker IDs remain opaque metadata, never path arguments. Worktrees live at `<repository-parent>/.amira-project-worktrees/<projectComponent>/iteration-<n>/`, outside the repository and outside Amira's agent `worktrees/` sweeper. A subdirectory project maps to the same repository-relative directory inside that checkout. Before checkout creation, every existing destination ancestor is checked for links/redirects and pinned by directory identity; pins are rechecked across human confirmation and immediately before `worktree add`. Canonical containment beneath the designated worktree parent and outside the repository is checked independently of ID derivation. Post-creation/root checks remain a second barrier; this is not protection against the final OS-level race of a hostile concurrent directory swap. Root, branch, common Git directory and base ancestry are also checked before execution and after checks. Never reuse a shared cwd on failure, adopt a colliding branch, auto-merge, push or remove a worktree. A failed/partially completed planned setup blocks automatic retry: inspect the saved artifact and Git state; preserve valuable work and resolve it deliberately rather than deleting evidence.

Canonical evidence stays under the **original** project's `.amira/project/iterations/<n>/artifacts/`, not a copied worktree marker. `iteration-worktree-<UUID>.json` stores setup intent/result, base, excluded-input preview and mapped cwd. `batch-result-<UUID>.json` stores exact approval/attempt identity, batch-base/end tree object IDs, `git diff --stat` between those snapshots, the child summary, actual implementer models from child metadata, and command records (cwd, exact command, timestamps, status, exit code and output). For new publications and active approvals/execution, every declared exact check must be attached to at least one spec item; unsupported orphan/global checks are rejected at those boundaries, not when reading historical artifacts. Every batch result must contain the complete approved required-check set exactly once, with its exact command and mapped cwd. Unrun checks after interruption are explicitly recorded as blocked, not executed or passed. Nonzero, denied, timed-out or cancelled checks never become passing evidence. Finishing implementation is **not** acceptance, even when its checks pass; failed checks are retained for the next review.

A fresh persisted coordinator per batch/attempt uses key `<projectId>/iteration/<n>/batch/<b>/implement/<attempt>`, mapped cwd, `descendants: "inherit"` and a worktree-root file-tool write ceiling. Its dedicated `project_implement` tool can spawn exactly **one** real fresh child through its owned group, with no caller-selected alternate task/cwd. Child input contains the user-language summary, English batch items, relevant verified decisions, confirmed prototype pointers/run instructions, worktree identity and required checks—not a fork, patch or transcript. No generic auto-merging agent/worktree tool is exposed. Actual metadata models, not requested defaults, are recorded.

The coordinator remains focusable for inspection; F6 returns to main. Finished/interrupted coordinators reject new model/tool activity until a new approved attempt is created. Native Stop is terminal for the batch even though an owned handle can normally be restarted: coordinator status and aborted-turn/tool evidence are checked before the extension's intentional drain, cancellation is latched through all independent checks and publication, and no subsequent check or acceptance proposal is started after cancellation. Cancellation during unapproved finalization retires its summary/proposal while retaining artifacts and changes; it cannot undo a human-confirmed transition. Revisit interruption stops and physically drains the coordinator/descendants before the engine records the transition, preserving checkout changes. Restart, attachment and panel rendering are inert: no tool/model call, replay, child restart or auto-continuation. A stranded running attempt can be explicitly interrupted with `/project revisit`; interrupted work needs the existing `/project next` continuation gate and a fresh attempt. The stage result proceeds through **implementation finished → saved summary → propose acceptance**; acceptance execution is the next implementation step.

**Non-sandbox boundary:** file tools are worktree-scoped, but approved shell commands/imported programs and trusted extension code can write elsewhere. No permissions are silently widened. Tool allowlists are not an OS sandbox, cannot prevent semantic copying, and do not certify check scripts as safe/offline. Review commands and production imports/build inputs yourself. Prototype code is never promoted by the extension; references are advisory, not proof of copying or safety.

## Design notes

- **D122:** durable batch coordinator plus one actual implementation child; workflow/swarm adapters are deferred and will use services, not imports.
- **Spec generation:** text-only `complete` rather than a saved read-only generator. This avoids unnecessary model tool authority; the extension validates/writes immutable artifacts and reuses step-one plans/receipts. Check `cwd` is relative to the mapped project directory (legacy checks default to `.`); `..` can reach repository-wide checks but never escape the worktree. Existing design/prototype stage summaries are retained when revising their spec draft; the rendered review and pinned approval identify the new spec/plan.
- **Launch is separate:** spec approval authorizes the first batch but never automatically starts it. `/project implement` performs Git setup with explicit base/dirty/bootstrap review. The approved model is the main session's model at review time; the real child's metadata model is stored separately.
- **Location:** repository-sibling `.amira-project-worktrees`, not extension-data-directory worktrees. Offline frontend testing reproduced Windows Git's filename-length failure with the host's long extension data path; sibling placement avoids that common limit without changing Git configuration. Name slug + safe ID component avoids collisions; an existing branch/path is never silently reused. There is no recovery/adoption/delete command in this step.
- **Opaque identity and destination safety (acceptance fixes):** preserve normal lowercase safe IDs and otherwise derive a single `id-<SHA-256>` path/ref component; do not restrict or rewrite existing marker metadata. Worktree paths must independently remain beneath `<repository-parent>/.amira-project-worktrees/<component>/iteration-<n>`. Existing destination ancestors must be canonical, non-linked directories with unchanged dev/inode/birth identity before creation, including across the base dialog. Ready artifacts pointing outside that boundary are refused, never adopted or deleted. Permission-checked Git remains the creator; preflight does not create directories in trusted extension code.
- **Cancellation lifecycle (acceptance fix):** subscribe to coordinator abort evidence before sending, inspect its stopped state before intentional drain, and carry a sticky abort signal through every subsequent owned tool and finalization boundary. The store's separate `interrupt-batch` event can retire an active implementation's unapproved finished/summarized/proposed state without broadening ordinary `interrupt-work` or erasing human-confirmed acceptance. Aborted work retains complete check records with explicitly blocked not-run commands.
- **Spec item lineage and checks (acceptance fixes):** generated artifacts store `lineage.previousSpec` (exact artifact ID/revision/hash), per-item `id`/`previousId`, and explicit `retiredItemIds`. The model supplies `previousItemId` for continuations, `null` for additions, and a top-level retirement list; its item IDs are draft labels for batch mapping, not allocation authority. The extension assigns monotonically increasing `S<n>` IDs to additions and never recycles a historical ID. An unchanged requirement cannot masquerade as an addition plus retirement. The store independently validates lineage and required check identities/commands/cwds at publication. Legacy specs lacking lineage remain readable when otherwise valid; a new legacy-format revision may edit only the same existing ID set. Previously valid orphan-check artifacts remain readable as unchanged history. Current policy rejects new orphan publications/approvals/work starts, including a legacy launch authorization; publish or generate a corrected revision instead of editing old evidence. This is structural identity enforcement, not semantic inference: humans still review whether a declared edit or retirement is appropriate. Exact global/orphan checks are not supported; attach a shared check to the relevant items, and it runs once per applicable batch.
- **Historical schema versus active policy (round-2 acceptance fix):** artifact reads/recovery validate the historical payload shape, immutable identity and hashes only. Current check mapping is enforced when publishing a spec or a spec-bound artifact, approving work or passing completion, consuming active evidence, or starting work. Explicit skip/interrupt bookkeeping is not an approval to execute or a passing outcome. Historical plan/acceptance binding validation explicitly uses history mode; active authorization explicitly uses active mode. A superseded orphan revision cannot brick an otherwise healthy iteration or prevent a corrected revision from being approved and executed. The executor checks mapping before opening any setup conversation or issuing Git commands. No legacy artifact/journal is rewritten or re-approved by opening it.
- **Next-menu dismissal (round-2 acceptance fix):** optional actions have named values, not array-slot identity. An undefined or unoffered selection immediately returns the saved state; Escape does not withdraw the proposal, advance its revision, or invoke generation. The other select sites were audited: variable project/variant pickers guard missing selections before lookup, and fixed spec/prototype/reason/stage options do not compare cancellation with an absent slot. Intentional spec-review cancellation remains a separate draft-withdrawal action.
- **Setup owner:** a separate saved, shell-only, no-file-write setup coordinator runs at the canonical project cwd, because the implementation owner's cwd must already exist. Each explicit setup gets a fresh key; both setup and implementation owner histories are retained. All Git commands still go through owned `runTool`.
- **Batch base:** a temporary Git index records beginning/end tree objects, including untracked files, with `read-tree`, `add -A` and `write-tree`. It never changes the real index/branch or creates a batch commit; Git clean filters still apply under the ordinary shell permission boundary. The temporary index is removed, not the worktree. These snapshots make later uncommitted batches' diff stats relative to their own batch inputs rather than cumulative HEAD changes. Successful clean/CRLF-conversion warnings remain in the owned tool evidence; snapshot parsing requires one unambiguous tree hash and never disables the user's Git conversion configuration.
- **Spawn seam:** the coordinator's extension-owned `project_implement` tool has an empty schema and a fixed seed; it uses `createGroup(maxAgents: 1)` and withholds spawn tools from the child. This is a normal host tool, not a second agent loop or the generic agent extension's auto-merge runner. After child completion, owned stop/drain precedes independent exact checks.
- **Prototype advisory:** implementation uses added diff lines through `runTool` for a small literal-reference advisory, preserving the prototype step's non-blocking advisory decision. It does not invoke the full scanner's direct Git probes in the execution path, and cannot detect semantic code copying.

## Development and offline verification

```sh
cd extensions/project
bun install
bun run link-amira ../../../Amira
bun run typecheck
bun run lint
bun test
```

`link-amira` links **only `@amira/*`** packages from the checkout. The relative path above assumes the Amira and extension-repository checkouts are siblings; replace it with your checkout location. Dependencies are extension-local. The test preload creates temporary HOME/USERPROFILE/AMIRA_HOME/cwd, removes live flags/credentials, and blocks fetch. Tests use mock dialects and temporary project directories; no real home, model API or GUI is required.

Host-source tests discover the checkout in this order:

1. `AMIRA_SOURCE`, when set, selects the checkout explicitly. An invalid explicit location does not fall back to another checkout.
2. Otherwise, the real filesystem targets of linked `@amira/*` packages identify the checkout.

No machine-specific checkout path is assumed. If source is unavailable, a required host export is missing, or a host module cannot be imported, affected cases are registered as clear skips with a reason and one shared source notice per process. Extension-only tests still run. Failures inside a loaded test are test failures, not skips. Install and link the development packages before running typecheck or tests; source discovery does not replace dependencies.

To select a prepared checkout explicitly from `extensions/project`, use an absolute resolved path so the isolated test cwd does not affect it:

```sh
# POSIX
AMIRA_SOURCE="$(cd ../../../Amira && pwd)" bun test
```

```powershell
# PowerShell
$env:AMIRA_SOURCE = (Resolve-Path ../../../Amira).Path
bun test
Remove-Item Env:AMIRA_SOURCE
```

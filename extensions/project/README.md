# Project (experimental)

Project discovery, a persistent design conversation, an auditable record of **human** decisions, isolated prototype variants, and iteration state with human-confirmed stage gates for design → prototype → implementation → acceptance. Prototype work is available through explicitly opened variant conversations. English spec/mode review, explicitly started single-agent, workflow or swarm batches, fresh reviewer acceptance and correction batches are available. Durable reported-spend accounting and project-level caps are available. Explicitly approved shipping supports local merge (default) and GitHub PRs through `gh`. Explicit iteration closure, archive/restore and separately approved safe cleanup are available. Dashboard integration is **not available yet**. Advancing a stage never starts implementation automatically.

Requires Amira extension API **^0.1.65**, including owned `usage()`, inert `read()`, text-only `complete()` and owned archive support. No workflow, swarm, btw or dashboard dependency.

## Commands

Run commands from the **main** conversation:

| Command | Action |
| --- | --- |
| `/project` or `/project list` | Choose from previously opened projects plus the nearest discovered project. No disk scanning. |
| `/project new [name] [--root <directory>] [--language <tag>] [--commit-documents]` | Create and attach a project. Without a name, ask for one. Default directory: current working directory. Quote names/directories containing spaces. |
| `/project switch [name, id, or directory]` | Attach a known/discovered project, or open an explicit directory. Without an argument, show the picker. Duplicate names require an ID or directory. |
| `/project status` | Show attached directory, iteration, real stage/status, pending approval, manual-trial status, and accepted/skipped/unresolved batches of the pinned plan. |
| `/project cost` | Reconcile reported costs and display project, iteration, stage, session and child rollups, coverage and cap state. |
| `/project cost cap <USD>` / `raise <USD>` | Explicitly set or raise the attached project's cap. Raising must exceed its current cap. |
| `/project cost continue` | Record explicit continuation at the current subtotal and acknowledge the current incomplete/estimated pricing scope. Does not restart stopped attempts; new reported spend is checked again. |
| `/project cost remove` | Explicitly remove the project cap and record that choice. Does not restart work. |
| `/project next` | Show the current saved summary and proposed next step; ask you to confirm, choose an alternative or skip. A batch pass proposes fresh approval of the next batch, not overall completion. No implementation starts automatically; from implementation planning, offers spec generation and review. Escape dismisses the next-step menu without changing its saved proposal or generating a spec. |
| `/project skip <stage>` | Ask you to explicitly skip the current stage (`design`, `prototype`, `implement`, `accept`). Skipping acceptance lists and records every remaining pinned-plan batch as skipped, not passed. |
| `/project skip batch` | From a non-running pinned implementation or acceptance boundary, explicitly skip the current batch. Interrupt running work first. Its receipt identifies the exact plan/batch; remaining work still needs human approval. |
| `/project revisit design\|prototype` | Return to an earlier stage without resetting changes. During implementation/review, choose interruption or waiting until the batch finishes. |
| `/project design` | Open this project's saved design conversation for the current iteration. |
| `/project prototype` | Propose, edit or remove variants, then confirm a list of 1–3 variants before opening prototype work. |
| `/project prototype <variant>` | Focus the saved conversation for a confirmed variant in this iteration. Opening it does not start a model turn. |
| `/project prototype choose` | Choose a recorded variant or None, then enter a separate human reason or explicitly skip the reason. |
| `/project prototype run <variant>` | Display only the recorded run command and working directory. Never execute it or start a server. |
| `/project spec` | Generate an English spec from verified decisions and confirmed prototype conclusions, with a user-language summary. Choose a compatible execution mode when available, review the rendered items/checks/plan, approve that exact revision/hash, mode and plan, request regeneration with feedback, or cancel. From design, approval explicitly skips prototype. |
| `/project mode` | Change execution mode for the current idle approved batch without regenerating the spec. Retain verified completed/skipped batches, schedule only unresolved work, keep the selected batch, and require fresh approval of the replacement plan. For interrupted work, review continuation with `/project next` first. |
| `/project implement` | Start the approved batch in its approved execution mode after committed-base/Git setup review, or focus its live coordinator. Repair attempts receive the preserved failure evidence. F6 returns to main without stopping it. |
| `/project accept` | Start a fresh owned reviewer for the exact acceptance batch approved with `/project next`, or focus the live reviewer. Runs independent exact checks through current permissions. |
| `/project ship` | Review release notes, the consumed completion boundary, exact candidate files/commit, full checks and repository integration preference; confirm each effect separately. Never starts from acceptance automatically. |
| `/project ship status` | Read the saved ship summary, check outputs, local-only/skipped outcomes and partial or uncertain operations without running tools. |
| `/project ship reconcile` | Explicitly inspect uncertain Git/hosting results or PR merge state; restore a durable successful push as `pushed`, without replay. Hosting reads require normal permissions and may access the selected remote. |
| `/project ship local-only` | Explicitly skip an unperformed/declined push after verified local integration and full checks. Refuses after a successful push, or for an unmerged PR handoff. |
| `/project ship revise` | Preserve settled operation evidence and review a replacement plan after repair. Reconcile uncertain effects first. |
| `/project ship skip` | Explicitly skip ship without claiming checks passed, a merge, push or publication. No-code/document-only iterations need no invented Git operation. |
| `/project iteration` | Read lifecycle and closure/archive receipts without starting work. |
| `/project iteration <number>` | Read an explicit historical iteration without repairing or initializing storage. |
| `/project iteration close` | Confirm closing the shipped or explicitly ship-skipped iteration; drain and archive its owned conversations. Retain all resources. |
| `/project iteration new` | Confirm starting the next iteration after closure. Create fresh state/owner keys; do not launch a model, worker or worktree. |
| `/project archive` | Confirm ending the project. Fence admissions, drain all inventoried runtimes and archive their owned histories. Hide the project by default; retain all resources. Repeat explicitly to recover a partial archive. |
| `/project list --archived` | Include archived/pending projects for explicit read-only lookup. `/project switch <id or directory>` also resolves hidden projects. |
| `/project restore` | Confirm restoring project metadata only; never resume old workers or revive their approvals. |
| `/project iteration continue` | Review exact restored stage inputs and record fresh continuation approval. Retire an archived running attempt as interrupted; `/project next` then obtains normal fresh attempt approval. Only eligible current design/prototype conversations can be unarchived. No work starts. |
| `/project iteration recover` | Explicitly recover interrupted local lifecycle publication, without replaying tools or host operations. |
| `/project iteration cleanup [worktree\|branch\|prototypes] [iteration]` | Preview and separately confirm optional safe cleanup. No forced Git deletion. Prototype deletion keeps manifests, choices, reasons and decisions. |
| `/project help` | Show command help and the batch boundary. |

Example: `/project new "Local planner" --root "./work/planner" --language en`.

**Attaching is metadata-only:** the main conversation's working directory does not change. The design conversation and research children use the selected project directory. One project is attached per main session. Attachments follow that session's branch (including resume/fork/rewind); the latest snapshot wins. An attachment receipt is persisted even before the first model prompt. Memory-only hosts cannot promise next-run attachment persistence.

The panel above the input shows name, iteration, the persisted stage/status and the next-step suggestion. It does not infer approval from tool completion or start work while rendering. Before opening design it says “Open design conversation.” Once a design runtime is available it uses a neutral continuation/F6 return hint, not a command to open the conversation again. Host panels receive the main session ID even during native design focus, so the extension does not claim to infer focus from that ID. The host's native focus indicator identifies the actual composer target. The normal panel-collapse control leaves the summary line visible. Missing/invalid status appears before long paths in picker labels; the extension never silently substitutes a nearby project.

## Closing, archiving and restoring

Acceptance completion is **not** shipping or iteration closure. Legacy `phase: complete` remains an open, unshipped iteration. After completed ship or an explicit ship skip, `/project iteration close` records a separate human receipt, publishes a close-pending admission fence, drains the iteration's owned work and archives its executable histories through the host. The project stays active. `/project iteration new` separately initializes fresh state and owner keys, seeded later from project design and decisions—not raw previous conversation history. It starts no model, provider, child, worktree or cleanup. Old iteration journals/artifacts retain their bytes and remain readable with `/project iteration <number>`.

`/project archive` means **end the project**, not delete it. Its marker is authoritative: an archive-pending fence rejects new launches, stale native handles, late questions/provider callbacks and ordinary document/artifact writers before drainage. The inventory includes design/research, prototype variants and predecessors, spec/proposal generation, setup/freshness/correction tools, implement/review workers, every bound provider group and ship/check owners, including failed/cancelled attempts and keys whose ID publication crashed. Original retained provider objects and owned scopes are stopped and drained; H3 archives each resolved owner. Durable pending-open intents prevent another process's not-yet-published identity from being certified absent; live or unverified openings block completion. An explicit retry also handles H3's intentional refusal to read an incomplete archive, retrying only its project-scoped key before verifying identity again. Final H1 usage is reconciled after H3, including after restart, without opening a runtime or adopting cap defaults. Main and other projects are not stopped.

A failed drain, inventory read or host archive leaves the marker **pending/read-only** and records a **failed operation** with actionable errors in `lifecycle-operations.json` and `/project iteration`. It is not presented as fully archived. A throwing provider `stop(runId)`, or a refused stop whose original provider can no longer observe the run, fails drainage instead of waiting indefinitely for a result that may never arrive. This is not settlement: the original result subscription and stop authority remain retained. After repairing the original provider, explicitly repeat the same archive/close command to recheck it; no provider run is restarted or replayed. A genuinely delayed finalizer still waits for the original `onResult`, including when stop returns false but the run remains observable—neither ended groups nor a terminal status snapshot certifies provider settlement. A foreign-process writer must settle first. `/project iteration recover` confirms recovery of an interrupted *local storage publication* only; it does not replay host operations or start work. If a continuation's marker committed but its result record did not, explicitly repeating `/project iteration continue` matches the saved receipt and repairs only that local result—no host operation or stage work is replayed. Reads never recover or repair records.

Archived/pending projects are hidden from the default registry/discovery picker. A hidden nearest marker still shadows outer projects: there is no fallback to an outer active project. Use `/project list --archived` or `/project switch <id or directory>` for explicit lookup, then `/project status`, `/project cost`, `/project ship status` or `/project iteration <number>` for inert history. These historical reads do not initialize accounting, run Git/model tools, repair journals, scan prototype boundaries or write project/registry files. Default-list filtering is not the enforcement mechanism; storage and the host independently reject stale writers.

`/project restore` changes project metadata only, preserving identity, design, decisions, iteration IDs and costs. No conversation, question, worker, provider or prior execution stack resumes. Closed iteration conversations remain archived; request `/project iteration new` separately. For an interrupted open iteration, explicitly confirm `/project iteration continue` and then follow the normal stage gates. Restore leaves an open iteration read-only until this fresh continuation receipt approves its exact stage revision/spec/batch/mode context. Only eligible current-stage design/prototype conversations with retained code may be unarchived; predecessor, removed-prototype and old worker conversations remain historical. Continuation starts no execution; unfinished work still follows normal stage gates.

### Optional cleanup: retain by default

Neither close nor archive removes a worktree, branch, prototype or conversation. `/project iteration cleanup` without a resource only shows guidance. Select `worktree`, `branch` or `prototypes`, optionally followed by an iteration number, to inspect it through an inert, shell-only owned tool context. Inspection permission is **not deletion approval**: each exact preview (identity, HEAD, preserved ref and disposable file list) receives a separate human confirmation and durable requested/result receipt in `cleanup.json`.

Git cleanup requires recorded project-owned path/branch/common-dir identity, all inventoried project users (including other iterations) archived, an idle main conversation outside the resource with no active/unknown child or group users, verified ship preservation/ancestry, and a clean supported checkout/index. The host cannot enumerate unrelated extensions, foreign sessions or OS processes: you must separately verify and attest that none use the exact resource; if that is unknown, cancel and retain it. That scoped attestation is saved with the deletion receipt, not inferred from tool permission. This is not a global process-exclusion guarantee. Dirty, staged, untracked, **ignored** or empty untracked directories, submodules, symlinks/junctions, moved refs/paths, hidden index flags and unfinished merges block deletion. Use only ordinary `git worktree remove` and, after that exact removal, separately confirmed `git branch -d`. There is no forced fallback, hard reset, recursive filesystem fallback, global prune/sweeper or automatic retry of uncertain effects. Squash/unmerged branches without ancestry evidence are retained. Inspect and reconcile requested/uncertain cleanup receipts manually rather than replaying removal.

Prototype code deletion is independent and variant-specific. Permanent manifests, selected-variant rationale, design, decisions and conversation history stay intact. Removal receipts mark disposable code removed/unavailable; requested or uncertain cleanup takes precedence even if the immutable manifest still says `planned`, `building` or `failed`. Historical views suppress directory, cwd and run-command pointers for those unavailable variants, even if partial deletion left some files behind. The old run command is historical evidence, not a newly runnable path. Spec and worker inputs retain the confirmed conclusion but omit removed/unavailable code pointers. A later prototype cleanup skips previously removed variants and reports requested/uncertain receipts without replay, so remaining retained variants can still be selected for separately approved removal. Cleanup never deletes host session files. This is application/host enforcement, not OS ACL protection against external editors or a sandbox for approved shell commands.

## Execution modes

`/project spec` discovers optional services at review time. Single agent is always available. Workflow and swarm are offered only when `workflow.runner` or `swarm.runner` provides `available`, `startBound`, `status`, `stop`, `onProgress`, `onResult`, returns **`true` from `available()`**, and advertises **all five** capabilities as `true`: `cwd`, `freshRun`, `models`, `ownedLifetime`, and `progress`. The provider's own enabled/confirmation settings still apply; a project approval does not bypass a provider confirmation. An installed package or dashboard service alone is insufficient. The settings-aware `available(): true | { reason: string }` contract requires workflow/swarm **0.3.1 or later**; a service missing it is incompatible. `enabled: "never"` removes the mode from recommendations. Availability is checked again before launch, during liveness polling, and before accepting result callbacks, so disabling a running provider stops the original run, retains changes, and records its reason. Older providers remain unsupported for project execution.

The recommendation favors a single agent for one small task, workflow for multiple ordered batches, and swarm for a batch with multiple items that can be assigned to collaborators. Workflow runs a fresh implementation child per item in order; swarm assigns items to members that coordinate shared-file edits (a one-item swarm includes a research-only collaborator). You choose the mode, then approve it **together with the exact spec revision/hash, plan hash, batch and requested model**. Choosing a mode alone never authorizes execution. Escape dismisses the mode menu without approval. Advancing a stage never starts a runner.

`/project implement` rediscovers the service before Git setup and again before starting a **new bound run for each batch**, including repairs. It passes the iteration worktree execution cwd and an owner bound to that batch's fresh owned coordinator: session ID, label, cancellation signal and `createGroup`. There is no provider-code import, legacy `start` fallback, resumed provider run, or main-session group substitution. The panel and `/project status` show live phase, children and effective models. Batch-result artifacts persist actual model references, run/group/child session IDs and effective cwd independently of the optional extensions. Provider settlement and coordinator drain precede independent checks and the normal acceptance flow.

A missing, old, disabled, unloaded or replaced provider, capability loss, or a mismatched effective cwd stops/blocks the approved mode with a recorded reason. **Project never silently switches mode or cwd.** Changes stay in the iteration worktree. A single-agent fallback is offered through **`/project mode`**, not spec regeneration. If interrupted, first use `/project next` to review continuation. Choose Single agent and approve the exact replacement mode/plan before `/project implement`. The immutable spec, requested model, iteration worktree and selected batch stay fixed: accepted B1 remains accepted and approved B2 stays selected; only unresolved batches are scheduled. Completed/skipped batches retain their original plan-qualified verdicts, trial results and human receipts through `modeChange.previousPlan` and exact carried-resolution references—no verdict is relabelled or copied to fabricate acceptance. Earlier skipped work still makes overall completion “skipped — not a pass.” Publishing the replacement retires the old launch authorization; the old receipt cannot approve the new mode. Escape at mode selection changes no state; Escape at reapproval leaves the saved proposal unapproved for later `/project next`. Withdrawing that proposal or stopping review after plan publication retains a recoverable mode-only draft: `/project mode` or `/project next` re-reviews the same plan, without restoring old launch permission or regenerating requirements. `modeChange.sourceApprovalId` anchors the original source context for that recovery; only a new human receipt authorizes execution. `/project spec` remains the requirements-generation path and is not a mode-only fallback. Restoring the originally approved compatible service does not itself start work.

Stop and interrupting revisits cancel the owner and call the original runner's `stop`; waiting-at-boundary revisits let the batch settle first. F6 returns to main without stopping work. Restart is inert: saved state/results remain readable even with neither provider nor dashboard installed; interrupted execution is never replayed automatically.

## Shipping: local merge and GitHub PRs

`/project ship` is an explicit, recoverable sequence, not “merge HEAD.” Implementation normally leaves accepted work **uncommitted**; batch snapshots are tree objects, not branch commits. Ship resolves every consumed, human-confirmed, plan-qualified accepted or skipped batch (including carried/preserved historical evidence and correction obligations). Missing evidence is **unavailable**, changed approval/decisions are **stale**, and skipped requirements remain **not passed**. It does not use the active-only acceptance freshness display helper after completion clears the active attempt. Before preparing notes, it reconstructs the last consumed review's exact context/reference window and checks its current checkout fingerprint. If that authority is unavailable (including a legitimate intervening commit/index change or skipped acceptance), it requires an explicit **current-content acceptance waiver**, recorded as skipped/not passed; it never interprets a missing verdict or a HEAD-sensitive mismatch as a fresh passing review. Fresh full candidate and integrated checks remain mandatory even after that waiver.

1. Drain this process's design, prototype, implementation, review and original optional-service writers. Serialize durable plan/intent/result publications through the project writer claim and revision checks; do not hold that claim across tools/accounting drain. Pin the recorded iteration worktree, canonical repository/common Git directory, branch/HEAD, all nonignored file inputs and real index, plus an explicitly chosen clean target checkout/branch/HEAD. Another process or external editor can still change Git; pins are revalidated before effects, not an OS sandbox.
2. Enter release notes in your language **after source/target identity has been pinned**. Follow an existing `CHANGELOG.md`, `CHANGES.md`, `HISTORY.md` or `docs/changelog.md` convention, with an exact append confirmation; immediately revalidate repository/common-dir identity, branch, HEAD and completion evidence after the dialog and before the permission-checked write. Movement stops preparation without writing notes to another branch or resetting it. Include the confirmed notes edit in the candidate before checks. With no such convention, store immutable iteration summary/notes artifacts instead of creating a root changelog. No version, tag or channel is invented.
3. Choose exact repository-relative deliverable files as a JSON array; inspect the **complete incoming delta and source-only commit history**, not only changes since source HEAD. The target's pinned merge-base, earlier iteration commits (including committed deletions and reverted/add-then-delete paths), and selected working changes all participate in review. Every incoming path needs explicit review; forbidden prototype, obvious secret or project-control paths stop shipping even when they were committed before ship or subsequently removed. Repair such history yourself—project never rewrites it. Unrelated dirty/staged files can remain excluded when they are not in the candidate/history. An isolated temporary index constructs/commits the reviewed candidate while preserving the real index, including partial staging. Afterward Git may show selected files as staged/unstaged relative to the advanced HEAD; project deliberately does not reset your real index.
4. Approve **all current item-bound checks**, including carried/preserved requirements, plus an explicit supplemental ship-only full-suite manifest when needed. Enter `[]` only when item checks really cover the complete delivered product. **Source checks never run in the dirty iteration checkout.** Each runs in the plan's pinned `checkRoot`: deterministic owned `runTool` steps create a detached temporary Git worktree at the pinned source HEAD, populate its own index/files with the exact candidate tree, verify it before/after the check, then restore only that disposable index/files with a non-forcing two-way `read-tree` and use ordinary `git worktree remove`. No synthetic commit, invented identity, user checkout/index mutation or forced cleanup is used. Check receipts bind the exact tree, approved absolute phase-specific cwd, command, output, exit code, timeout and cancellation—not just an `ok` flag. Integrated receipts bind the separately pinned delivered tree in the selected target checkout. Missing tree provenance, a wrong cwd or an unsafe older passing receipt cannot authorize effects or lifecycle settlement. Source/check input movement, new nonignored files or failed cleanup block shipping before commit/integration/push. Dirty, redirected or interrupted temporary checkouts are retained at the recorded path for explicit inspection; an existing check path is never silently adopted or force-removed. A revised plan gets a fresh check path. Submodules, symlinks, special files and redirected paths are unsupported and block shipping; ignored inputs, toolchain/environment, Git metadata-dependent behavior and arbitrary build scripts are not universally attested. Review dependency setup/check commands for this isolated checkout; scripts remain trusted code under normal permissions, not a sandbox.
5. Confirm the exact candidate commit. Normal signing, clean filters and repository hooks apply. Verify the resulting tree/parent and raw inputs: hook-modified deliverables stop integration and require repair, new checks and approval. Existing exact commits can be rechecked without manufacturing another commit.
6. First use asks for local merge (default) or PR and the repository-native fast-forward-only/merge-commit policy; remember the preference and target per common Git directory, **not permission to mutate**. Each use still selects/revalidates a clean target checkout. Project never checks out, resets, stashes, aborts a merge or cleans your main worktree. Conflicts stop with evidence for explicit repair. Reconciliation validates supported delivered inputs as well as exact ancestry/parents, cleanliness and identity; even a clean, explicitly repaired merge containing a gitlink/symlink/special file is retained but cannot progress to checks, push or completion. Run the complete checks again on the exact integrated result before any push/completion.
7. Push and `gh pr create` each require a **separate confirmation every time**, bound to the exact commit, remote URL/name, branch/ref and PR repository/base/title/body. PR mode necessarily permits a separately approved preparatory source-branch push. A PR is **awaiting-merge**, not shipped. Explicit reconciliation verifies the same PR/candidate and merge commit; update the selected target checkout yourself to that exact merge commit, then complete integrated checks and approve completion. Squash/merge results are checked, not assumed equal to the source.

Durable plans, preference, approvals, requested intents, check results and operation receipts live in `.amira/project/ship.json`; fallback notes live under the immutable iteration artifacts. The sequence uses an otherwise inert, inventoried/accounted owner and deterministic permission-checked `runTool` calls. It never sends a model a shell task for irreversible steps. Host auto/allow permission is **not** product approval. Approved checks/hooks are trusted repository code and may have their own effects: inspect them, and approve any external effect explicitly rather than hiding it inside a generic check.

Each effect is independent. A successful local integration followed by a push refusal/timeout is partial progress; it is not merged again on resume. A crash after commit/merge but before a receipt is reconciled through exact tree/parent/ref evidence. A requested/uncertain remote operation is **never blindly retried**; unavailable or ambiguous observations remain blocked. A durable successful push is recovered as **`pushed`** after interruption, without replaying commit/merge/push or replacing its exact passing receipts. A successful target push cannot be relabelled skipped or local-only, including through persisted-state injection or lifecycle settlement. In PR mode you may still explicitly abandon/skip the unmerged ship; its preparatory source-branch push remains recorded as successful (never skipped), and no target integration is claimed. Outward preflight has an explicit dispatch fence: URL/ref validation, command/body preparation or cancellation that fails **before** `git push`/`gh pr create` is handed to `runTool` is recorded as a known `failed` operation with `effectNotStarted` evidence. It preserves the exact approval/inputs and permits a newly approved revision, local-only completion for an unstarted local push, or explicit PR abandonment while preserving the successful preparatory push. It is not automatically retried. Once a mutation has been dispatched, errors/timeouts or failed post-dispatch observations stay **uncertain**; an absent remote ref or PR is never proof of non-application. Reconciliation preserves the known preflight failure without querying absence to manufacture that proof. Known no-effect local failures can be reconciled as failed, repaired and explicitly revised. Hook/signing failure, policy denial and cancellation never trigger weaker flags or a fallback shell. No force push (including force-with-lease), hook/signing bypass, invented identity or ref replacement is generated. No automatic rollback occurs.

Declining an operation is recorded, not treated as success. Confirm **local-only** after local integration to explicitly skip push; an unmerged PR cannot be relabelled delivered. Explicit ship skip supports no-code/document-only work and waivers without fabricated checks or Git operations. Ship does not close the iteration, end the project or delete iteration branches/worktrees, prototypes or history. Only its newly created, clean disposable check worktrees are normally removed.

**D135 v1 boundary:** only local merge and GitHub PR through `gh` are implemented. There are **no tag, release, package-publishing, repository-creation, CI-creation or deployment adapters**. `ship-pr.ts` documents the extension point: a future explicitly selected adapter must take the checked immutable commit plus its own per-operation approval and durable receipt; no adapter runs by default. Workflow/swarm/dashboard remain optional and are not imported.

## Reported costs and project caps

The project panel shows known reported USD and the project cap/stop state. Restored attachments hydrate that cache through an inert background read at session start, not by initializing accounting or reading costs during rendering; historical display writes nothing. `/project cost` provides alternate rollups by iteration, stage, owned session and child. Stage rollups remain available, but **v1 has only a project-level cap** (D135): no stage-cap settings or stage latches. Caps default to unlimited. The extension setting **Default project cap (USD)** applies only when a project first initializes accounting; leave it empty for no cap. Existing project policies change only through the explicit cost commands.

Accounting lives in `.amira/project/costs.json`, separately from stage approvals. The extension persists each intended owned key and its attribution **before opening**, and binds the returned session ID before work. A crash between creation and ID binding is reconciled through the host's inert key reader, never by guessing a private session ID. The inventory includes design/research, prototype variants and predecessors, spec/proposal generation, coordinators, implementation/review/repair attempts, and otherwise-zero-cost setup/check owners. Recovery derives identity-file candidates from this project's keys, historical manifests and trusted ledger bindings before parsing them; unrelated corrupt identity files cannot block a healthy project, while corruption in its own records still fails closed. Spec and prototype proposals share one text-only owned `complete()` helper: malformed output, errors, retries and cancellation remain charged by the host.

The ledger replaces cumulative snapshots by host accounting revision, including signed downward corrections. Root own usage plus disjoint descendant own usage is counted once. Every workflow/swarm group is retained, including sibling workflow groups created by swarm members; group/provider totals are **not added again**. A removed optional provider does not remove its historical costs. Main-chat attachment is metadata-only: unrelated main activity and other projects are not charged to this project.

At **80%**, warn once per cap policy. At **100% or above**, latch admission closed immediately, abort pending owned/provider work, stop the captured original providers, end retained groups and stop **and release** all affected project owners. Ledger I/O happens after cancellation starts. The latch survives restart and downward corrections. Implementation bindings are cancelled and their interrupted-result publication is drained before continuation; cleanup remains idempotent when budget enforcement has already released a handle. Stale focused handles cannot resume work; after an explicit cost-policy choice, approve a fresh continuation/attempt and reopen the saved identity as appropriate. Failed reconciliation/persistence blocks new work rather than claiming enforcement from stale evidence. Accounting observers run independently of panel/dashboard visibility and reconcile on events, drain and bounded inert refreshes.

Unknown prices are **not zero**. Display known USD, tokens and incomplete/estimated coverage. Uncapped projects can keep working with that disclosure. An outstanding request fence is **pending accounting**, not an unpriced receipt. Pending activity is tracked per session: a busy sibling cannot hide another child's settled accounting gap. The host's pricing helper is sampled before serialization so genuinely unpriced or estimated receipt evidence remains distinct from that pending state. Known USD is enforced immediately, even during a request. The public `complete` flag alone does not identify its failure reason, so opaque/inert or foreign-writer coverage remains conservative; a host `pendingOnly` field (true only when pending requests are the sole gap, false for mixed integrity/pricing failures) is the requested follow-up for precise classification without runtime activity. Unknown-price/coverage blocking is applied at settlement or a new-work admission boundary, without cancelling an ordinary priced request merely because it is still in flight. A capped project stops at that safe boundary when new incomplete/unpriced/estimated usage prevents meaningful enforcement. Configure model pricing, or use `/project cost continue` to record a durable acknowledgement of the current scope. New unknown evidence needs another acknowledgement. Existing projects retain recoverable owner costs and disclose unavailable pre-upgrade main-bound calls; the extension never estimates old invoices from token counts. Policy changes and acknowledgements are retained as receipts.

A ledger revision conflict is not a transient write failure: the cached revision is fenced and is **not retried**. Reload the project extension, then run `/project cost` again to read the authoritative ledger; do not delete or rewrite cost evidence. Ordinary temporary storage failures can still be reconciled with `/project cost` once storage is available.

**This is a reported-spend stop, not a hard financial guarantee.** In-flight requests, cancellation latency, late receipts and missing provider usage can exceed a nominal cap. Stop/completion does not certify invoice finality. Continue/raise/remove never transparently resumes a workflow stack or restores an old launch approval. No host-wide budget or unrelated main owner is changed.

## Discovery and files

The nearest ancestor containing `.amira/project.json` wins, including nested projects inside one repository. A malformed nearest marker is an error, not permission to fall back to an outer project. An explicit switch resolves its directory/registry identity independently of cwd discovery, so you can recover by switching to a healthy project. Lists retain healthy registry entries alongside a visible discovery warning. A directory has exactly one project marker. The registry in the host-assigned extension `dataDir` only remembers projects opened before; it never scans search roots or your disk. Registry writes publish independent immutable transactions in `registry.entries/`, so different Amira processes cannot lose each other's read–modify–write updates. Legacy registry snapshots are still read. Healthy explicitly reopened locations outrank stale same-ID locations even if the wall clock moved backwards; stale identities remain visible when no healthy location exists.

The extension's document writers use only fixed documents, evidence and generated research-note filenames. Prototype code is written separately through host file tools scoped to a confirmed variant directory. Canonical root, ancestor and output-directory identities are pinned when a project is captured, then checked again before writes and publication. Replacing a root or captured ancestor with a junction is rejected even if the redirected tree contains the same project marker. Traversal and symlink/junction escapes are rejected. External output directories are not supported in this batch. These are application safeguards, **not an OS sandbox**: portable Node APIs cannot eliminate the last kernel-call race against a hostile process continuously swapping directories. Allowed read tools may read outside the project according to host permissions.

## Lifecycle/storage groundwork

Acceptance and iteration closure are separate. Legacy `phase: complete` means **acceptance complete, iteration still open and unshipped**. Ship has its own pending/running/blocked/shipped/explicitly-skipped state; closing requires a settled ship outcome and a separate receipt. Project lifecycle is active → archive-pending → archived, with an explicit inert restore. **Closure remains explicit:** a completed or explicitly skipped ship outcome leaves the iteration open until `/project iteration close`. Close/archive invoke owned H3 archival after a durable fence and drainage; next iteration, restoration and optional cleanup each require separate actions. There is no runtime replay or automatic deletion.

Legacy marker schema 1 and immutable stage journals remain readable without rewriting evidence. Publishing lifecycle-bearing state upgrades the marker to schema 2, so older extensions reject it rather than treating closed/archived work as executable. A project-level claim coordinates lifecycle intent, fresh next-iteration storage and marker publication; explicit recovery completes interrupted local publication without executing work. Claims do not depend on the old current-iteration pointer and conservatively recover dead writers without stealing live claims.

`HistoricalIterationReader(project, iteration)` selects an explicit iteration and performs no initialization, projection repair, writer claims or filesystem writes—even after the current marker advances or the project is archived. Unsupported/corrupt evidence is preserved and rejected, not repaired while browsing. Ordinary document, decision, artifact, stage, prototype and retained-dialog writers check current lifecycle and reject stale or read-only selections. Settled accounting uses the separate administrative machine-document path, so late receipts/corrections remain durable after an admission fence without granting new execution authority.

## Iteration stages and approval gates

State lives in `.amira/project/iterations/<n>/state.json`, not the host session database. It records `schemaVersion`, monotonic `revision`, project/iteration identity, stage (`design`, `prototype`, `implement`, `accept`), status (`idle`, `working`, `awaiting-confirmation`, `interrupted`, `blocked`), skips, human approval receipts and immutable artifact links. Opening an old batch-one project creates **design / idle** state lazily; it never rewrites old documents or decision evidence. Reopening state is inert: it never replays a launch.

The reducer keeps these events separate: **work finished → summary prepared → transition proposed → human confirmed → next stage started**. A model recommendation or a tool finishing is not approval. Proposals are saved before a human dialog, and receipts bind the exact project, iteration and state revision. Implementation/review authorization also pins the **spec revision/hash and immutable batch-plan artifact ID/hash**, batch ID and mode (plus the implementation model). Batch membership is resolved only from that pinned plan, never from the newest plan or any plan with the same batch label. Publishing a replacement plan invalidates an idle confirmed launch authorization; a new summary and same-stage `reapprove` proposal require fresh human confirmation. Plan replacement is refused while work or approval is in progress. Dismissing a dialog creates no approval receipt. If anything changes while a dialog is open, the stale answer fails; review the new state and confirm again. The state store serializes writers, uses a cross-process claim, and rejects stale revisions rather than silently overwriting another writer.

Each artifact has a closed kind and an extension-generated filename under the iteration directory; titles, model output and supplied text never choose output paths. The kinds cover stage summaries, spec revisions with stable item IDs, batch plans, acceptance verdicts keyed by spec item ID with actual check records, manual trials (`pending`, `tried`, `problem`, `deferred`), and corrections/impact. Artifacts are immutable; edits are detected instead of overwritten. State publication flushes files and uses an atomic, no-clobber hard link for each immutable journal record; `state.json` is a safely replaced projection, with directory flushes where supported. A journal record is the commit boundary: recovery validates all referenced artifact envelopes and batch metadata **before** repairing an older/missing projection or writing its acknowledgement, and never replays work. Unsupported or invalid referenced evidence leaves the old projection bytes/inode and acknowledgement state untouched. A live cross-process claim fails clearly; a dead process's claim is recovered with a token-specific recovery claim. Manual edits to state or artifacts block further writes and remain byte-identical. Preserve retained versions when recovering a crash or manual edit.

Batch membership is recorded in store-owned `batchManifests`, copied from hash-checked plan artifacts, and progress in plan-bound `batchResolutions`. A consumed batch pass and its resolved manual trial become accepted progress only through a human-confirmed transition. `/project next` presents the batch summary and proposes the **next unresolved batch** for fresh implementation approval, with the exact spec/plan/batch/mode/model context. Confirming it leaves implementation idle; it does not start an executor, and it never carries the previous batch's changes pointer into the new work. A cancelled or stale dialog records no batch resolution or launch authorization.

**Overall acceptance is not a single-batch verdict.** Completion is proposed only after every batch of the pinned plan has a confirmed passing resolution or an explicit human skip. If any batch was skipped, overall completion is labelled **skipped — not a pass**, never “Accepted.” Failing, blocked, interrupted, merely published, or manual-trial-pending verdicts do not resolve a batch; earlier plan/spec revisions cannot satisfy a new plan. Legacy draft completion is interpreted only from verified consumed evidence and human receipts, never by inventing outcomes for remaining batches; historical bytes are not rewritten.

Corrections use **qualified `acceptedBatches` references**, not bare batch labels. Each reference identifies the owning spec artifact/revision/hash, plan artifact/hash, batch ID, accepted-resolution human receipt, and consumed review attempt. Both publication and correction consumption require an actual confirmed, accepted `batchResolution` with matching passing evidence and any required resolved trial. Published-only, interrupted, unconfirmed, pending-trial, skipped, and same-label/different-plan results do not qualify. A correction targeting a revised spec may reference a genuinely accepted batch of an older plan; that older owner's identity remains explicit. Legacy unqualified claims are not silently promoted into accepted evidence.

Each acceptance start captures a fresh **stage-attempt ID, review ordinal and code-snapshot hash**. Verdicts and manual-trial artifacts bind all three, along with the exact spec and batch plan, at both publication and consumption. A verdict saved for an interrupted attempt remains readable history; a continuation needs a new attempt and new verdict, even when the code snapshot is unchanged. Merely copying a batch label or increasing a numeric attempt field cannot authorize stale evidence.

Skips retain your choice and never fabricate output: a skipped prototype has no chosen variant, and skipped acceptance is **not passed**. Acceptance failure retains failing spec item IDs and proposes a human-approved return to implementation; it never starts a hidden retry loop. An automated UI pass is **automated pass, manual trial pending** until you record that you tried it or explicitly deferred it; deferred never means tried, and the batch cannot advance or complete while the trial is unresolved. A human-confirmed **problem** on the active attempt proposes a separate, human-confirmed repair back to implementation for that same pinned spec/plan/batch. The automated verdict remains unchanged, and the manual finding/receipt remain history. The repair needs fresh implementation, acceptance, and trial evidence before that batch can be accepted; simply changing the old problem to tried/deferred is not a repair. Pending transitions and unresolved revisits take precedence over trial dialogs. Interrupting or leaving a review retires its live trial pointer while preserving attempt-bound trial artifacts as history; explicit continuation never resurrects an interrupted attempt's trial. Trial recording is offered only for the matching eligible active review.

Revisiting design/prototype during implementation or acceptance interrupts the running attempt and retains its changes pointer, or queues the revisit until a safe batch boundary if you choose to wait. Pending revisit requests are separate from returned/cancelled revisit history and correction obligations. “Continue current stage” explicitly cancels the outstanding request as well as its proposal; it does not silently resume interrupted work or erase duties from already-returned visits. An unentered cancelled request requires no invented correction; explicit continuation can resume against the unchanged approved decisions. A restart between summary publication and proposal publication reuses the saved summary to reconstruct the pending revisit. Returning and advancing again permits another revisit without losing earlier receipts or unresolved obligations. Accepted **and skipped** acceptance leave the iteration open: a confirmed revisit clears the current completion designation while preserving historical verdicts/skips. Existing changes and earlier artifacts remain; there is no Git reset, transcript rewind or prototype promotion. Correction artifacts link superseded → new decision IDs, affected spec item IDs and changed files, so later execution can approve a correction batch rather than restart from scratch. Every outstanding executable-work correction must be mapped against a revised spec before execution can resume. Spec generation after a revisit maps verified superseding decisions to affected items and changed files, publishes a correction revision/plan and requires approval. The same branch/worktree is reused without reset; identical accepted requirements can be carried forward only with their qualified passing evidence.

`/project next` does not invent a completed summary. If no stage output is ready it explains the missing gate. You can continue design or explicitly skip it. Saved design can be finalized into a summary with its confirmed decision IDs, then proposed for the next stage. “Continue current stage” cancels a pending proposal and invalidates the prepared design summary. A stranded design attempt after a crash requires explicit interruption/continuation confirmation; the interrupted record is retained. Design writers share the iteration claim, invalidate captured state revisions before publication, and reject late questions after a revision or stage change. During a stage change the local design runtime is stopped/drained before confirmation is committed. Completing or skipping prototype can enter implementation **preparation only**, without authorizing execution. Starting implementation still requires the exact saved spec/batch/mode/model approval; acceptance still needs the approved existing-change context. `/project spec` produces those pinned artifacts and approvals. `/project implement` is a separate explicit launch. At the acceptance boundary `/project next` proposes and confirms acceptance; `/project accept` or the named next-step start action then launches it separately. Ship starts only with explicit `/project ship`. Prototype conversations are opened explicitly with `/project prototype` commands, not by advancing a stage.

Storage failures expose structured diagnostic reasons. Commands and panel errors use the effective batch-one language policy (`en`/`zh`/`ja`), including stale revision numbers and recovery actions. A freshly validated marker supplies the language even if iteration loading fails immediately, including after resume without a panel refresh. Unsupported numeric schema versions in markers, journals, state and artifact envelopes report encountered/supported versions and compatibility instructions, separately from malformed data or a broken hash chain; no such error is repaired by deleting or rewriting evidence. Artifact compatibility tests use coherent hashes and projection receipts, and verify byte preservation.

## Design conversation

There is **one owned conversation per project ID and iteration**. Reopening is inert: it does not call a model or replay an unfinished question. Enter a message to continue. A new iteration uses `design.md` and `decisions.md`, never the previous iteration's transcript. New projects start at iteration 1; `/project iteration new` explicitly advances only after closure and opens no conversation.

The native transcript and composer are shared visually, not operationally. Main work keeps running. **F6** returns to main; **Esc** also returns when the design conversation is idle and its composer is empty. While design is working, Esc/Ctrl+C stops design only. Drafts, history and question dialogs are handled by the host. Slash commands must be run after returning to main. The host focus indicator shows main status/pending attention.

Design history survives main `/clear` and `/resume`. Closing focus does not stop/release it. A second process holding the design conversation gets an **in use** error. Host unload/exit stops and releases runtime resources without deleting saved history. Unsupported hosts explain the missing capability; there is no ephemeral-session fallback.

### Tools and questions

Research operations are restricted to `read`, `grep`, `glob`, `web_search`, `web_fetch`. `ask_user` and the fixed extension tools `record_decision`, `record_suggestion`, `save_research_note`, `update_design_doc` and `project_research` provide the control plane and constrained output writes. No arbitrary `write`, `edit`, shell, `agent`, worktree, workflow or swarm tools are admitted. Web availability still depends on the host; the extension does not make its own network requests.

The model is instructed to lead with multiple-choice questions: recommended option first, each description explaining trade-offs. Previews are text, code, tables or ASCII only. Questions appear as normal human dialogs in the focused transcript. The extension never asks the main model to answer on your behalf.

`project_research` starts fresh-context, read-only children through the owned conversation's `createGroup`. Their tool ceiling cannot widen, their cwd is fixed, and they cannot ask or confirm decisions. Only the extension's constrained note writer saves research output.

### Evidence and recovery

Only validated human dialog answers become decisions. A model-authored recommendation remains in `suggestions.md`. Each decision retains an ID, actual confirmation date, full question/options/trade-offs, exact selected labels or free-text alternative answer, language, and an ask-record reference. “Other” is an alternative choice, **not** a rationale. No reason is inferred from it or from a model recommendation; a rationale requires a separately requested human explanation. Cancelled, unavailable, aborted or invalid responses do not create decisions.

Before returning an answer to the model, the extension durably writes structured evidence under `.amira/project/` (JSON lines, with file flush). Cancellation is checked after entering the per-project queue and immediately before publication. The final identity check, rename, directory flush where supported, and cleanup form a short non-yielding commit section. The owner receipt **does not wait on Markdown I/O after that commit**: a later ordinary event-loop Stop cannot overtake its acknowledgment. Cancellation processed before publication produces no decision; successful publication is the extension's commit boundary. `SessionData.append` is not used as a durability acknowledgment.

Markdown is a derived projection, scheduled separately after owner-answer acknowledgment and retried on the next design open. Projection failures/conflicts are reported separately, never turned into a false declined/no-decision receipt. A process crash between evidence publication and host acknowledgment cannot be a filesystem/host transaction; the durable human evidence remains authoritative and recovery does not infer a new answer from prose. Superseding requires a new human confirmation and preserves the old record (`supersedes D3`, with the reverse link in the ledger).

Generation metadata tracks `decisions.md`'s hash. If you edit it by hand—even during generation—the extension preserves the actual edited inode and generates a sibling `decisions.generated.md`. Publication uses retained versions plus no-clobber hardlinks, not a stale hash check followed by unconditional replacement. Design/suggestion tools likewise report conflicts and their actual sibling output paths instead of claiming the named file was updated. Hardlink support is required; unsupported filesystems fail before moving the original.

Hidden `.preserved` versions intentionally remain: an editor holding an old writable descriptor may still save into one. Do not remove them while editors may hold those files. There is a brief pathname gap between retaining an old file and publishing its replacement; after a crash, a retained version may need restoring, especially for human-only annotations. The evidence can always regenerate confirmed decisions, but cannot reconstruct handwritten annotations that were never evidence. Do not manually edit evidence or generation metadata.

Legacy evidence from the rejected writer remains byte-for-byte intact and its original hash chain is verified separately. Corrected semantic views, Markdown and new-iteration model seeds no longer treat its automatic `Other` copy as a rationale; they mark that legacy explanation as unverified. New projection records explicitly distinguish this corrected interpretation from historical bytes.

## Prototype stage

At the prototype stage, `/project prototype` presents a **proposal**, not an approved plan. Review the proposed variants, edit their descriptions or remove variants, and explicitly confirm the final **1–3 variant** list. Model suggestions, a dismissed dialog and an edited draft are not confirmation. Variant work belongs to the current project and iteration; reopening saved work does not replay a launch or begin a model turn.

Each confirmed variant has its own conversation. Send the build request in its focused native composer; opening or reopening is inert. The model finishes with one run command and a structured report; the extension validates its cwd and saves the manifest, rather than letting the model edit stage artifacts. `/project status` and prototype commands refresh completed reports. The extension requires API ^0.1.64; prototype capability guards also fail closed rather than starting an unconfined session or falling back to main-bound generation. `/project prototype <variant>` focuses it through the host's native conversation UI; return to main before issuing project commands. Host **file-tool writes have exactly one allowed root per variant**, `.amira/project/prototypes/<iteration>/<variant>/`, not the production project root or a sibling variant. The host enforces that write scope for file tools; reads still follow host permissions. Shell tools still use the **current permission mode**: a variant cwd is **not a shell sandbox**, and shell commands may affect files outside that directory if host permissions allow them. Review permissions and commands accordingly.

New variant conversations use `<projectId>/iteration/<n>/prototype/<variant>` and the host's `apply_patch` tool. Older saved conversations with the mistaken `patch` ceiling are not widened or rewritten. Read-only inspection remains on the old conversation; explicitly reopening it for editing creates a bounded `/policy/apply_patch-v1` conversation and preserves the previous ID/transcript in the extension-owned mapping. A notice identifies both sessions, and no messages or commands are replayed.

Prototype directories are ignored by default with `.amira/project/`, subject to the existing `--commit-documents` setting and your `.gitignore`. They are disposable exploration, not production implementation. Choosing a variant **never promotes or copies its code into production**, changes production imports, or starts implementation. Comparison is **read-only**: inspect recorded summaries, trade-offs and results without modifying variants or executing their programs.

Use `/project prototype choose` to explicitly select a variant or **None**. The human reason is requested separately from the choice: enter your explanation or explicitly choose **Skip reason**. An empty or cancelled reason is not an implicit skip, and neither an option label nor a model recommendation is treated as your explanation. Choosing None retains the findings without selecting code. To skip the stage itself, use `/project skip prototype` and explicitly confirm the skip. A skipped stage has no chosen variant and does not invent a successful prototype. If you decline a prototype skip, `/project next` → **Continue current stage** abandons that skip summary and restores a confirmed/idle editing boundary. Reopen a variant explicitly to continue; earlier attempts, files and decision evidence remain history, and no work or command is replayed.

`/project prototype run <variant>` **only displays the recorded command and cwd** so you can inspect and run them yourself. It never executes a command, installs packages, opens a browser, starts a server or automatically restarts anything. Missing run information is not permission to infer a command. A `ready` status means the model supplied a structurally valid report with an in-variant cwd; it is not an independent claim that the command was executed or passed checks. Comparison's file count is the current prototype output tree, excluding `.git`, `node_modules` and symlinks, not a production Git diff.

Prototype decisions use evidence **format version 3**: the selected variant (or None), immutable manifest pointers and separately captured `reason` or `reasonSkipped` are recorded together. Existing v1/v2 evidence and hash-chain semantics remain byte-identical. A restart finishes missing choice/summary bookkeeping from this evidence without asking again or duplicating decisions, and never replays prototype work. A confirmed revisit reopens the variant list while retaining prior conclusions, files and native transcripts. A revised selection—including None—automatically supersedes the prior active prototype conclusion for that iteration. Recovery preserves those supersession links without duplicating decisions. Historical evidence remains readable even if disposable prototype output is removed; opening or displaying a runnable command validates the current paths again.

### Advisory: references to the prototype directory

`scanProductionPrototypeReferences(root)` in `src/prototype-boundary.ts` is a **read-only conservative text scan**, not an import parser, dependency audit or isolation guarantee. It returns `{ file, line, column, text }`: project-relative forward-slash filenames, one-based source lines and UTF-16 columns, and the original matched namespace text (including escapes). `formatPrototypeReferenceReport()` prints `file:line:column` and that matched text under the header **“Advisory: references to the prototype directory.”** The old `scanProductionPrototypeImports` export remains a compatibility alias, but its results are now references, not import violations.

Each physical source line is searched for `.amira/project/prototypes` after decoding JavaScript `\\xNN`, `\\uNNNN` and `\\u{...}` escapes and CSS hexadecimal escapes (with optional terminating whitespace), normalizing backslashes/repeated slashes, and folding ASCII case. This catches template expressions, parentheses, erased TS wrappers and all entries in Sass lists without interpreting their syntax. **Comments, ordinary strings, regexes and JSX text may also be flagged**, including references that are not actual imports; inspect their context. Path fragments split across lines or assembled by concatenation are **not reconstructed**, and dot-segment paths, aliases and computed module resolution are not evaluated. No project code/configuration or run command is executed, and no TypeScript/compiler/parser runtime dependency is required. TypeScript remains a development dependency for typechecking only.

The file set is JS/TS (`js`, `jsx`, `ts`, `tsx` and their `c`/`m` forms), CSS/SCSS/Sass/Less, and common configuration files (`json`, `jsonc`, `yaml`, `yml`, `toml`, `ini`, `cfg`, `conf`, `config`, `.env`/`.env.*`, dot-rc files, `.gitignore` and `.gitattributes`). The project's `.amira/project` tree, `.git` and `node_modules` are hard exclusions. Conventional build/cache names (`dist`, `build`, `out`, `target`, `coverage`, `.next`, `.nuxt`, `.output`, `.svelte-kit`, `.cache`, `.turbo`, `.vite` and `.parcel-cache`) are heuristics **only for untracked paths**. A read-only `git ls-files` snapshot keeps tracked source/style/config files and the ancestor directories needed to reach them eligible—even under names such as `src/build` or `src/target`. Untracked output siblings remain excluded, and tracked status never overrides the hard exclusions or symlink safeguards. Native Git supplies the effective ignore rules, including parent/nested `.gitignore`, `.git/info/exclude`, configured `core.excludesFile`, default user excludes, negations and tracked-file semantics. Inherited Git directory/index/config-injection/trace overrides are stripped; hooks and executable filesystem monitors are disabled. Non-Git projects use temporary Git metadata outside the project to honor local `.gitignore` files. Git is required for filtering; there are no hooks, index writes, network requests or source-tree initialization.

Implementation and acceptance **show advisories, never automatically block on their matches**. The implementation result includes an added-diff-line advisory gathered through the coordinator shell (not the scanner's direct Git probes); it does not prove the absence of copied code or dependencies. The complete source-tree scanner remains available for manual advisory presentation. Use `reportProductionPrototypeReferences(root)` for presentation: scan failures are shown as **“Scan unavailable”**, not as a clean result or an automatic failure of the stage. The low-level scanner still throws on filesystem/Git failures. Descendant symlinks/junctions and source-file links are not followed; a linked root is rejected and canonical paths/file identities are checked before reading. This is not an OS sandbox against hostile concurrent directory replacement. Run the offline regressions with `bun test test/prototype-boundary.test.ts test/prototype-scan-ignore.test.ts`.

## Spec and implementation

`/project next` offers spec generation from the design next-step menu or after prototype/implementation planning. You can also run `/project spec` directly after design, after a confirmed prototype choice, or after explicitly skipping prototype. Generation uses text-only `complete` with **no tools and no inherited conversation history**. Only verified, non-superseded decisions, the human-confirmed prototype choice/pointers and prior spec revisions enter it; neither design Markdown nor the design transcript is supplied. A feedback regeneration retains immutable old specs/plans. Stable item identity is enforced by extension-controlled, predecessor-bound lineage, not prompt compliance alone: edits retain an existing ID, additions receive fresh extension IDs, and removals must be explicit. Silent renumbering is rejected before publication. Malformed output, unknown decision IDs, missing check cwd, orphan exact checks, or incomplete batch coverage fails closed.

The rendered review starts with a summary in the effective document language, then the English goal/constraints, numbered stable-ID items, per-item acceptance criteria, exact check commands and their cwd, and an ordered batch plan with the chosen execution mode. It shows the spec/plan hashes, requested implementation model and any skipped prototype stage before approval. A pending approval reopened with `/project next` renders the pinned spec/plan again. Approval is an existing stage-engine human receipt, not a model assertion. No Git or implementation starts from the review. Use `/project implement` separately.

Git discovery, setup, snapshots and checks use **owned `runTool` shell calls under your current permissions/rules**, never `api.runCommand` after an unrelated confirmation. Plan mode or a denied command stops setup. Every initial setup shows the exact committed HEAD, repository, destination branch/worktree and dirty/untracked preview. You may stop and resolve local changes or explicitly exclude **all displayed local changes** from that commit. No stash, copy, hidden dirty snapshot or silent omission is used. Both status probes use `--ignore-submodules=none`: configured submodule ignore modes cannot hide staged/unstaged/untracked contents or a changed submodule HEAD. The preview is checked again before setup.

For an empty/no-commit project, confirm `git init` if needed plus an **empty initial commit** before setup. Existing files are never staged. A staged index blocks the empty commit. Git uses your existing identity, signing and hooks; failure stops with the command/error, with **no** `--no-verify`, signing override, alternate hooks or identity injection. Resolve it yourself and retry. Stack/dependency/test scaffolding belongs in the approved first batch's worktree, not the original directory.

The extension journals a planned worktree artifact before creation and a ready artifact after verification. The branch is `amira/project/<projectSlug>/iteration-<n>`; the slug includes a normalized name plus a filesystem/ref-safe component derived from the stable project ID, distinguishing same-named/subdirectory projects. Normal lowercase generated IDs retain their spelling; unsafe, case-ambiguous, or reserved IDs use an `id-<SHA-256>` component. Marker IDs remain opaque metadata, never path arguments. Worktrees live at `<repository-parent>/.amira-project-worktrees/<projectComponent>/iteration-<n>/`, outside the repository and outside Amira's agent `worktrees/` sweeper. A subdirectory project maps to the same repository-relative directory inside that checkout. Before checkout creation, every existing destination ancestor is checked for links/redirects and pinned by directory identity; pins are rechecked across human confirmation and immediately before `worktree add`. Canonical containment beneath the designated worktree parent and outside the repository is checked independently of ID derivation. Post-creation/root checks remain a second barrier; this is not protection against the final OS-level race of a hostile concurrent directory swap. Root, branch, common Git directory and base ancestry are also checked before execution and after checks. Never reuse a shared cwd on failure, adopt a colliding branch, auto-merge, push or remove a worktree. A failed/partially completed planned setup blocks automatic retry: inspect the saved artifact and Git state; preserve valuable work and resolve it deliberately rather than deleting evidence.

Canonical evidence stays under the **original** project's `.amira/project/iterations/<n>/artifacts/`, not a copied worktree marker. `iteration-worktree-<UUID>.json` stores setup intent/result, base, excluded-input preview and mapped cwd. `batch-result-<UUID>.json` stores exact approval/attempt identity, batch-base/end tree object IDs, `git diff --stat` between those snapshots, the child summary, actual implementer models from child metadata, exact changed filenames, and command records (cwd, exact command, timestamps, status, exit code and output). For new publications and active approvals/execution, every declared exact check must be attached to at least one spec item; unsupported orphan/global checks are rejected at those boundaries, not when reading historical artifacts. Every batch result must contain the complete approved required-check set exactly once, with its exact command and mapped cwd. Unrun checks after interruption are explicitly recorded as blocked, not executed or passed. Nonzero, denied, timed-out or cancelled checks never become passing evidence. Finishing implementation is **not** acceptance, even when its checks pass; failed checks are retained for the next review.

A fresh persisted coordinator per batch/attempt uses key `<projectId>/iteration/<n>/batch/<b>/implement/<attempt>`, mapped cwd, `descendants: "inherit"` and a worktree-root file-tool write ceiling. In single-agent mode its dedicated `project_implement` tool can spawn exactly **one** real fresh child through its owned group, with no caller-selected alternate task/cwd. Child input contains the user-language summary, English batch items, relevant verified decisions, confirmed prototype pointers/run instructions, worktree identity and required checks—not a fork, patch or transcript. No generic auto-merging agent/worktree tool is exposed. Actual metadata models, not requested defaults, are recorded.

The coordinator remains focusable for inspection; F6 returns to main. Finished/interrupted coordinators reject new model/tool activity until a new approved attempt is created. Native Stop is terminal for the batch even though an owned handle can normally be restarted: coordinator status and aborted-turn/tool evidence are checked before the extension's intentional drain, cancellation is latched through all independent checks and publication, and no subsequent check or acceptance proposal is started after cancellation. Cancellation during unapproved finalization retires its summary/proposal while retaining artifacts and changes; it cannot undo a human-confirmed transition. Revisit interruption stops and physically drains the coordinator/descendants before the engine records the transition, preserving checkout changes. Restart, attachment and panel rendering are inert: no tool/model call, replay, child restart or auto-continuation. A stranded running attempt can be explicitly interrupted with `/project revisit`; interrupted work needs the existing `/project next` continuation gate and a fresh attempt. The stage result proceeds through **implementation finished → saved summary → propose acceptance**; acceptance is separately approved and explicitly started with `/project accept`.

**Non-sandbox boundary:** file tools are worktree-scoped, but approved shell commands/imported programs and trusted extension code can write elsewhere. No permissions are silently widened. Tool allowlists are not an OS sandbox, cannot prevent semantic copying, and do not certify check scripts as safe/offline. Review commands and production imports/build inputs yourself. Prototype code is never promoted by the extension; references are advisory, not proof of copying or safety.

## Acceptance and correction loop

After implementation finishes, `/project next` reviews the batch result and confirms the pinned acceptance route. `/project accept` starts the reviewer; `/project next` also offers **Start acceptance review** at that approved boundary. Merely attaching, restarting, rendering a panel or confirming a stage never starts a model. An interrupted or blocked attempt needs explicit continuation and gets a new conversation/verdict. Escape and unoffered menu answers do not authorize work.

The extension setting **Reviewer model** (`reviewerModel`, a `provider/model` reference) defaults to empty. A configured reference must be locally available and differ from **every actual model that changed code in this batch**, including earlier repair attempts. Unknown references and collisions block launch with a clear error. With no setting, the extension uses an implementer model in a **fresh session**, labels the verdict **same-model**, and makes no model-diversity claim.

Each review uses `<projectId>/iteration/<n>/batch/<b>/accept/<attempt>` at the recorded iteration worktree cwd. Its seed contains the approved batch items and acceptance criteria, relevant verified decisions, prototype conclusions/run pointers, batch result/change pointers, implementer summary and exact required check commands. It never contains design or implementer conversation history. Reviewer file tools are read-only (`writeRoots: []`); shell runs under current host permissions. **Approved check subprocesses may still write files or have other side effects**. This is not a shell sandbox.

`project_record_acceptance` records structured `pass`, `fail`, `blocked` or `not-applicable` observations, evidence and reasons for **every** batch item ID exactly once. Prose alone cannot pass. The extension independently runs every required exact check through owned `runTool`, preserving command, mapped cwd, start/end timestamps, exit/error/timeout status and full returned output. Output pointers are the immutable acceptance artifact's `/checks/<index>/output` fields; the stage summary links that artifact. Missing, skipped, unsuccessful, timed-out or denied commands never pass. Plan mode produces a blocked attempt, not a successful review.

Verdicts bind the exact spec/plan/attempt plus a SHA-256 fingerprint of HEAD, tracked/untracked file contents and diff metadata, verified decisions and prototype inputs. The extension detects changes during review/checks. `/project status` explicitly rechecks freshness through policy-checked Git probes and updates the panel's **STALE** marker; passive rendering never executes commands. Before accepting a batch or recording its trial result, freshness is checked again. An unverifiable or changed input cannot consume the old pass; it retains the immutable verdict and requires a fresh attempt. The panel shows item counts, running/outcome status, same-model disclosure and manual-trial state; without a recent explicit probe it directs you to `/project status` rather than claiming freshness.

For UI items (`ui: true`, marked by the spec generator), an automated pass prepares a separate manual-trial artifact with working directory, verification instructions and observations from the approved spec. It remains **manual trial pending**, not fully passed, until you record **tried, OK** or explicitly **skip trial for now**. Deferral is recorded as `deferred (not tried)`. **Tried, problem** retains the human finding and enters the same repair gate as failed automated items. The extension does not launch a browser or pretend that running checks is a human trial.

A failed review publishes a summary listing failed IDs, reasons and evidence, then proposes a repair of the **same pinned batch** through confirmation. `/project implement` starts a fresh coordinator/child seeded with the failures; `/project accept` after the new approval creates a new verdict, never overwriting the old one. A pass with resolved trial proposes the next unresolved batch, or iteration-complete bookkeeping after the last batch. **Acceptance completion does not ship**; use `/project ship` for separately approved integration. Acceptance callbacks never merge, push, release, remove worktrees or close an iteration.

On **revisit design/prototype**, interruption is the first choice: stop/drain the current attempt immediately and keep its written changes. Waiting for the batch boundary is an explicit alternative. New verified superseding decisions produce a correction spec revision and `R<revision>-B<n>` batches mapping old decision → new decision → affected item IDs → exact filenames changed so far. Earlier accepted work/evidence and the branch/worktree are retained. Carry-forward is allowed only for semantically unchanged items with identical exact checks and qualified accepted evidence; changed or unresolved requirements get correction work. Interrupted attempts without a completed result get a separate, policy-checked changed-file probe in the retained worktree before generation. Its complete retained diff is conservatively mapped to affected requirements; denial blocks generation rather than inventing a clean diff. Legacy ambiguous diff-stat paths still remain explicit change pointers.

## Design notes

- **D122:** durable batch coordinator plus fresh implementation children; optional workflow/swarm adapters use structurally checked services, not imports. Acceptance runs directly in a fresh owned root with no descendants, using a schema recording tool and independently run exact checks.
- **Current decision policy:** new spec publication, active approval/continuation and execution reject missing or superseded decision references. A new review cannot silently adopt new decisions as the baseline of an obsolete spec. Historical loads remain schema-only, and blocked/stale evidence can still be saved without authorizing a pass. Revise the spec/correction and obtain fresh approval.
- **Reviewer cancellation:** reuse the owned lifecycle's sticky abort/end/stopped-state observation and drain barrier. Native Stop cannot start the next check or publish a pass; finished released owners are excluded from later quiescence. File fingerprints exclude mutable extension bookkeeping while explicitly binding verified inputs, so recording evidence cannot stale itself on committed-document routes.
- **Acceptance evidence:** deterministic command records are independent of model observations. Check output is embedded in immutable artifacts (JSON pointers rather than ephemeral console IDs). A completed failing verdict is never edited into a pass; repair and review each get fresh attempts. If policy denies the initial Git probes, the blocked record uses an all-zero hash sentinel with the verification error, not a claim of a verified code snapshot; it cannot authorize acceptance.
- **Freshness policy:** fingerprints include HEAD, byte-level tracked/untracked inputs and diff metadata, latest spec/plan and verified decision/prototype inputs. Permission-denied verification is unknown/stale, never fresh. Passive panels do not issue shell calls; explicit status and consumption gates do. Stale unconsumed reviews are retired as interrupted while preserving their verdict and trial history.
- **Manual-trial gate:** automated UI success remains pending until tried OK or an explicit deferral. Deferred is never tried. Cancellation before confirmation publishes no trial artifact/receipt. Trial instructions use approved verification/criteria; no guessed production launch command or automatic GUI launch.
- **Revisit obligations (acceptance review correction):** a confirmed revisit remains an execution obligation after design/prototype are skipped. Resolve outstanding receipts independently of the visible stage and record their correction mappings at idle planning boundaries before implementation approval—never start a synthetic implementation attempt to unlock bookkeeping. Mapping alone does not fulfill the obligation: canceled spec approval keeps the correction context and accepted-item preservation for regeneration until a human authorizes that exact mapped revision. Multiple pending receipts get separate immutable mapping artifacts. Cross-stage correction records require the matching confirmed revisit receipt; cancellation or a running implementation cannot authorize them. A revisit between accepted B1 and unstarted B2 sends no attempt-owned change pointers; existing artifacts retain the checkout and earlier work.
- **Correction scheduling:** retain the complete revised spec but schedule only changed/unresolved items; carry-forward requires qualified accepted evidence and unchanged item/check semantics, checked again by the store. New result artifacts record exact filenames; legacy diff-stat text is not parsed into filenames and remains an explicit change pointer.
- **Spec generation:** text-only `complete` rather than a saved read-only generator. This avoids unnecessary model tool authority; the extension validates/writes immutable artifacts and reuses step-one plans/receipts. Check `cwd` is relative to the mapped project directory (legacy checks default to `.`); `..` can reach repository-wide checks but never escape the worktree. Existing design/prototype stage summaries are retained when revising their spec draft; the rendered review and pinned approval identify the new spec/plan.
- **Launch is separate:** spec approval authorizes the first batch but never automatically starts it. `/project implement` performs Git setup with explicit base/dirty/bootstrap review. The approved model is the main session's model at review time; the real child's metadata model is stored separately.
- **Location:** repository-sibling `.amira-project-worktrees`, not extension-data-directory worktrees. Offline frontend testing reproduced Windows Git's filename-length failure with the host's long extension data path; sibling placement avoids that common limit without changing Git configuration. Name slug + safe ID component avoids collisions; an existing branch/path is never silently reused. There is no worktree adoption command; optional deletion is available only through separately confirmed safe lifecycle cleanup.
- **Opaque identity and destination safety (acceptance fixes):** preserve normal lowercase safe IDs and otherwise derive a single `id-<SHA-256>` path/ref component; do not restrict or rewrite existing marker metadata. Worktree paths must independently remain beneath `<repository-parent>/.amira-project-worktrees/<component>/iteration-<n>`. Existing destination ancestors must be canonical, non-linked directories with unchanged dev/inode/birth identity before creation, including across the base dialog. Ready artifacts pointing outside that boundary are refused, never adopted or deleted. Permission-checked Git remains the creator; preflight does not create directories in trusted extension code.
- **Cancellation lifecycle (acceptance fix):** subscribe to coordinator abort evidence before sending, inspect its stopped state before intentional drain, and carry a sticky abort signal through every subsequent owned tool and finalization boundary. The store's separate `interrupt-batch` event can retire an active implementation's unapproved finished/summarized/proposed state without broadening ordinary `interrupt-work` or erasing human-confirmed acceptance. Aborted work retains complete check records with explicitly blocked not-run commands.
- **Spec item lineage and checks (acceptance fixes):** generated artifacts store `lineage.previousSpec` (exact artifact ID/revision/hash), per-item `id`/`previousId`, and explicit `retiredItemIds`. The model supplies `previousItemId` for continuations, `null` for additions, and a top-level retirement list; its item IDs are draft labels for batch mapping, not allocation authority. The extension assigns monotonically increasing `S<n>` IDs to additions and never recycles a historical ID. An unchanged requirement cannot masquerade as an addition plus retirement. The store independently validates lineage and required check identities/commands/cwds at publication. Legacy specs lacking lineage remain readable when otherwise valid; a new legacy-format revision may edit only the same existing ID set. Previously valid orphan-check artifacts remain readable as unchanged history. Current policy rejects new orphan publications/approvals/work starts, including a legacy launch authorization; publish or generate a corrected revision instead of editing old evidence. This is structural identity enforcement, not semantic inference: humans still review whether a declared edit or retirement is appropriate. Exact global/orphan checks are not supported; attach a shared check to the relevant items, and it runs once per applicable batch.
- **Historical schema versus active policy (round-2 acceptance fix):** artifact reads/recovery validate the historical payload shape, immutable identity and hashes only. Current check mapping is enforced when publishing a spec or a spec-bound artifact, approving work or passing completion, consuming active evidence, or starting work. Explicit skip/interrupt bookkeeping is not an approval to execute or a passing outcome. Historical plan/acceptance binding validation explicitly uses history mode; active authorization explicitly uses active mode. A superseded orphan revision cannot brick an otherwise healthy iteration or prevent a corrected revision from being approved and executed. The executor checks mapping before opening any setup conversation or issuing Git commands. No legacy artifact/journal is rewritten or re-approved by opening it.
- **Next-menu dismissal (round-2 acceptance fix):** optional actions have named values, not array-slot identity. An undefined or unoffered selection immediately returns the saved state; Escape does not withdraw the proposal, advance its revision, or invoke generation. The other select sites were audited: variable project/variant pickers guard missing selections before lookup, and fixed spec/prototype/reason/stage options do not compare cancellation with an absent slot. Intentional spec-review cancellation remains a separate draft-withdrawal action.
- **Setup owner:** a separate saved, shell-only, no-file-write setup coordinator runs at the canonical project cwd, because the implementation owner's cwd must already exist. Each explicit setup gets a fresh key; both setup and implementation owner histories are retained. All Git commands still go through owned `runTool`.
- **Batch base:** a temporary Git index records beginning/end tree objects, including untracked files, with `read-tree`, `add -A` and `write-tree`. It never changes the real index/branch or creates a batch commit; Git clean filters still apply under the ordinary shell permission boundary. The temporary index is removed, not the worktree. These snapshots make later uncommitted batches' diff stats relative to their own batch inputs rather than cumulative HEAD changes. Successful clean/CRLF-conversion warnings remain in the owned tool evidence; snapshot parsing requires one unambiguous tree hash and never disables the user's Git conversion configuration.
- **Long-iteration reads:** journal bytes, retained projections and independent artifact validation use bounded eight-file read windows, while journal chain/schema checks remain ordered and every path/hash is checked on every transaction. No integrity cache is used. Implementation and acceptance current-state guards explicitly use a bounded **30-second interceptor timeout** (rather than the host's generic 5 seconds), so accumulated journal/claim validation can finish before a recording tool is admitted. The same current-state checks are still awaited, obsolete/cancelled calls stay blocked, and a tool-guard timeout remains fail-closed. Provider liveness polls publish only changed progress; live updates repaint without invalidating durable stage state. This avoids starving tool guards with repeated panel refreshes during multi-batch repair/correction flows.
- **Spawn seam:** the coordinator's extension-owned `project_implement` tool has an empty schema and a fixed seed; it uses `createGroup(maxAgents: 1)` and withholds spawn tools from the child. This is a normal host tool, not a second agent loop or the generic agent extension's auto-merge runner. After child completion, owned stop/drain precedes independent exact checks.
- **Prototype advisory:** implementation uses added diff lines through `runTool` for a small literal-reference advisory, preserving the prototype step's non-blocking advisory decision. It does not invoke the full scanner's direct Git probes in the execution path, and cannot detect semantic code copying.
